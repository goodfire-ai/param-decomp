# 3-Pool Training Dataflow Graph (GPT2-XL Q/K, b256 config)

Fresh-eyes semantic dataflow of the 3-pool decomposition step, annotated with concrete
shapes + dtypes per edge, plus a memory/bandwidth table and ranked inefficiency findings.

**Config** (`_b256_run/b256_lrA_comp5e-4.yaml`): B=256, S=1024, D=1600 (GPT2-XL d_model),
C=1024, V=50257, 96 sites (q/k of 48 layers). Topology 96 LW + 32 CI + 32 PPGD.
Per-rank batch: `bl_lw=256` (n_per_block=1), `bl_ci=8` (n_ci=32), `bl_pp=8` (n_ppgd=32).
CI fn = `GlobalSharedTransformerCiFn` d_model=4096, 8 blocks, mlp 16384, 32 heads,
total_input_dim = 96·1600 = 153 600, total_c = 96·1024 = 98 304. autocast bf16, fp32 master.

Notation on edges: `[shape] dtype`. "act-sized" = scales with B·S. "site-streamed" =
re-materialized once per owned site inside the LW per-site loop.

## 1. The graph

### CI pool (32 ranks, bl_ci=8) — `step_ci.py`

```
batch_T[8,1024] int64
   │ ci/0 (step0) or reuse prefetch
   ▼
target_fwd_and_cache  (ComponentGPT2 clean fwd, no_grad, bf16 autocast)
   │  H_T = 96 × pre_weight_acts                       [8,1024,1600] bf16 (autocast)
   │  ── UPCAST to fp32 in _target_fwd_and_cache ──►   [8,1024,1600] fp32   ×96  (≈5.0 GB)
   ▼
CI fn forward  calc_causal_importances(detach_inputs=False)
   │  rms_norm per site            96 × [8,1024,1600] fp32→(autocast bf16 matmuls)
   │  cat → concatenated           [8,1024,153600]  (bf16 under autocast; fp32 if input fp32 — see F-DTYPE-1)
   │  _input_projector (153600→4096)  GEMM
   │  8 × TransformerBlock @4096   [8,1024,4096] bf16
   │  _output_head (4096→98304)    GEMM → out  [8,1024,98304] bf16
   │  lower_leaky_fn(out), upper_leaky_fn(out), split→96
   ▼ CIOutputs (graph retained)
   ├─ lower_leaky : 96 × [8,1024,1024] bf16(autocast) ──┐
   ├─ upper_leaky : 96 × [8,1024,1024] ──► imp_min      │
   └─ pre_sigmoid : 96 × [8,1024,1024]  (unused in train)
                                                        │
  ci/2 SEND lower_leaky:                                │
    → LW   CiValuesToLayerwise   per-site, sub-sliced   │  pack→bf16 WIRE   (Σ 51.5 GB/step pool-wide)
    → PPGD CiValuesToPPGD        full-model, sub-sliced │  pack→bf16 WIRE   (Σ 51.5 GB/step pool-wide)
                                                        │
  ci/3 imp_min on upper_leaky:                          ▼
    per_component_lp_sums → [C] per site ; dist_fn.all_reduce SUM over CI pool (96 tensors, autograd-aware)
    finalize_imp_min → scalar
  ci/4 prefetch H_{T+1} (same as ci/0)   96 × [8,1024,1600] fp32
  ci/5 RECV g_CI from LW   → stitched 96 × [8,1024,1024] fp32  (recv bf16 → copy_ upcast fp32)
  ci/6 RECV g_CI from PPGD → stitched 96 × [8,1024,1024] fp32  (recv bf16 → copy_ upcast fp32)
  ci/7 g_total = lw + pgd  → 96 × [8,1024,1024] fp32
  ci/8 fused backward: backward(lower_leaky, grad=g_total) [retain] ; backward(coeff·imp)
        → CI fn param .grad  (2.64B params, fp32)
  ci/9 all_reduce_ci_fn_grads AVG (bucketed) over ci_pool_group
  ci/9b grad clip ; ci/10 AdamW(fused) ; ci/11 wait sends
```

### LW pool (96 ranks, 1 site each, bl_lw=256, activation-checkpointed) — `step_layerwise.py`

```
batch[256,1024] int64  (full batch — n_per_block=1)
   │
  A1 post_recv CI for owned site   PendingCiValues  → buf [256·1024·1024] bf16 WIRE (537 MB)
  A2 target_fwd (clean, no_grad, bf16, bypass_lm_head)
       target_local = hidden    [256,1024,1600] bf16  (838 MB)   (NOT logits: fused-KL)
   │
  C  param.grad = None
  D1 faithfulness: calc_weight_deltas() → (W_target − VU) [1600,1600] fp32 ; Σ(Δ²)/numel_global
       backward → V.grad,U.grad fp32
  D2 wait CI recv → _releaf_ci_fp32_for_grads:
       ci_s = recv.detach().to(fp32).clone().requires_grad_   [256,1024,1024] fp32 (1.07 GB)   ◄ F-DTYPE-2
  D3 per-site streaming loop (1 site here, but the loop is the general path):
       u   = rand_like(ci_s)          [256,1024,1024] fp32     ◄ F-RAND-1
       mask= ci_s + (1−ci_s)·u        [256,1024,1024] fp32  (3 act-sized ops)  ◄ F-MASK-1
       delta = target_weight − components.weight   [1600,1600] fp32 (VU recomputed)  ◄ F-DELTA-1
       delta_mask = rand(...)         [256,1024] fp32
       make_mask_infos → ComponentsMaskInfo
       pred = ComponentGPT2(batch, mask_infos)  CHECKPOINTED masked fwd → hidden [256,1024,1600] bf16
       fused_linear_kl_div(pred, target_local, lm_head_w[50257,1600])  chunked → (sum_kl, n)
       (coeff·loss/denom).backward()  → ci_s.grad fp32 ; V.grad,U.grad fp32 accumulate
  D4 send g_CI = ci_s.grad → CI pool   pack→bf16 WIRE  [256,1024,1024]→537 MB
  D5 recv g_VU from PPGD (leader recv + in-block bcast)  V,U [1600,1024] bf16→fp32
  D6 V.grad += g_vu ; U.grad += g_vu
  E  wait pending VU send ; all_reduce_grads_in_block (no-op, 1 rank) ; clip ; AdamW(fused)
     async send updated V/U → PPGD (bcast over {leader}∪PPGD)  bf16 WIRE
```

### PPGD pool (32 ranks, bl_pp=8, full V/U replica) — `step_ppgd.py`

```
batch[8,1024] int64
  A1 post_recv full-model CI   PendingCiValues → 96 × [8,1024,1024] bf16 (1.61 GB)
  A2 target_fwd (clean,no_grad,bf16,bypass) → target_out [8,1024,1600] bf16
  D1 weight_deltas = calc_weight_deltas()  96 × [1600,1600] fp32 (VU recomputed)
  D2 wait CI → releaf fp32: 96 × [8,1024,1024] fp32 .clone() (3.22 GB)  ◄ F-DTYPE-2
  D3 warmup: n_warmup_steps(=2) × { get_ppgd_mask_infos → masked fwd (NOT ckpt) →
        fused_KL recon sum → autograd.grad wrt sources only → PGD step }
        sources 96 × [8,1024,1025] fp32     ◄ each warmup iter rebuilds full fwd graph
  D4 (N+1)th recon fwd → sum_loss scalar
  D5 ONE autograd.grad(sum_loss, [V×96, U×96, ci_leaves×96, sources×96]) retain=False
        → raw g_V,g_U (fp32), g_CI (fp32), g_sources
  D5b send g_CI → CI  pack→bf16  96×[8,1024,1024]
  D6 sum_reduce_ppgd_grads SUM over ppgd_pool (V/U grads, bucketed)
  D6b ppgd_state.step(sources)
  D7 leader send g_VU → LW  bf16
  E  blocking recv updated V/U from LW → copy_ into model in place
```

| Edge | bytes/step (aggregate) | notes |
|---|---|---|
| CI→LW lower_leaky | 51.5 GB | 96 sites × [256,S,1024] |
| CI→PPGD lower_leaky | 51.5 GB | full-model × 32 ranks |

negligible by comparison. **pre_sigmoid is never sent in train** (good), but every CI

## 3. Inefficiency findings (ranked by expected payoff)

### F-DTYPE-2 — fp32 re-leaf `.clone()` of activation-sized CI on LW & PPGD ⭐ biggest
`step_layerwise.py:300-309` `_releaf_ci_fp32_for_grads` and `step_ppgd.py:273-280`:
```python
s: ci_recv[s].detach().to(torch.float32).clone().requires_grad_(True)
```
This is adjacent to the known mask issue but is a *distinct* op: `to(fp32)` + `.clone()`
allocates a fresh **1.07 GB fp32** tensor per LW site (and **3.22 GB** on PPGD), then the
whole masked forward runs the C-dim ops in fp32 because the leaf is fp32 (autocast does
not down-cast a fp32 leaf for elementwise/`mul`). Cost: a full-batch fp32 alloc + copy +
all the `aten::mul`/`add` in `mask = ci+(1-ci)u` at fp32 width — exactly the
bandwidth-bound profile observed.
**Why fp32 at all:** only so `ci_s.grad` accumulates in fp32 to merge into the CI-fn fp32
grads. But the grad is immediately packed back to **bf16** on the wire (`_pack_sites`).
**Fix:** keep the CI leaf in bf16 (`.detach().clone().requires_grad_()` with no upcast);
the per-site backward produces a bf16 grad, which is what gets sent anyway. The `.clone()`
is needed (re-leaf), but `to(fp32)` is pure overhead. Halves the CI-leaf allocation and
removes the fp32 mask arithmetic. Verify grad-balance with a one-backward RNG-pinned check
(per MEMORY: grad-scaling needs a real grad check, not loss curves).

### F-DTYPE-1 — H cache force-upcast to fp32 feeds the entire CI-fn forward ⭐
`step_ci.py:383-395` `_target_fwd_and_cache`:
```python
return {k: v.to(torch.float32) for k, v in cache.items()}
```
H_T is captured under bf16 autocast (so bf16), then **explicitly upcast to fp32** — 96 ×
[8,1024,1600] = **5.0 GB fp32** (10 GB counting the prefetch). The CI-fn forward then
`rms_norm`s fp32 inputs and `cat`s a **[8,1024,153600] fp32 = 5.0 GB** concat before the
input projector. Under autocast the projector GEMM down-casts to bf16 anyway, so the fp32
concat is a 5 GB write+read of pure cast churn on the critical-path pool.
**Open question (state, don't assert):** does `rms_norm`/`cat` run fp32 here? `cat` keeps
input dtype; `rms_norm` under autocast is typically kept fp32. Confirm by printing
`concatenated.dtype` in a 1-rank repro. **Fix:** drop the `.to(fp32)` — keep H bf16; let
autocast handle the projector. Saves ~5–10 GB and the cast. (The fp32 was likely
cargo-culted "CI fn wants fp32 inputs"; the projector is an autocast GEMM.)

### F-DELTA-1 — `calc_weight_deltas` recomputes VUᵀ redundantly, per site and per pool
`components.py:122-123` `weight = einsum(V,U)` (a [1600,1024]·[1024,1600] GEMM per site),
called from:
- LW D1 faithfulness (`calc_weight_deltas`, all owned),
- LW D3 **per site** again: `delta = target_weight - components.weight` (`step_layerwise.py:349`),
- PPGD D1 `calc_weight_deltas` (96 sites),
- PPGD warmup uses the deltas but they're stable across the 2 warmup iters (ok).

On LW the same site's VUᵀ is materialized twice per step (D1 then D3). Cheap per-site
(~6 MFLOP) but it's a fp32 GEMM + a full [1600,1600] subtract on the bandwidth-bound LW
rank, and the D3 one is inside the (general) per-site loop. **Fix:** compute `delta` once
per step (reuse the D1 `weight_deltas`) and thread it into D3 rather than recomputing.

### F-MASK-1 / F-RAND-1 — full-batch fp32 mask synthesis on the LW critical path
`step_layerwise.py:347-350`:
```python
u    = torch.rand_like(ci_s)              # [256,1024,1024] fp32  (1.07 GB alloc + RNG)
mask = ci_s + (1 - ci_s) * u             # 3 act-sized fp32 ops → 1.07 GB result
delta_mask = torch.rand(ci_s.shape[:-1]) # [256,1024]
```
This is the `aten::mul/add/copy_` that dominates the profile. Three things stack:
(1) it's fp32 (see F-DTYPE-2 — fixing that makes these bf16),
(2) `(1-ci)` and `ci+...` are separate kernels → 3 passes over a 1 GB tensor,
(3) `rand_like` is a 1 GB alloc + curand fill every site.
**Fix:** after bf16-ifying, fuse into one kernel — `torch.addcmul`-style or a small
`torch.compile`d elementwise — `mask = ci + u - ci*u`. Reuses one buffer, one pass.
The RNG alloc is unavoidable (stochastic source) but bf16 halves it.

### F-COMM-1 — CI values + grads cross the wire 4× at full activation size
CI→LW, CI→PPGD, LW→CI, PPGD→CI are each ~51.5 GB/step (≈206 GB aggregate). The forward
CI and the returning grad are the **same shape**; PPGD and LW both receive the full/owned
CI and both send a grad back. Two structural reductions:
- **bf16 is already used on the wire (good).** But the CI→PPGD send ships the *full model*
  CI to all 32 PPGD ranks (each gets a [8,S,96·1024] slice) — total still 51.5 GB because
  it's batch-sharded, fine. No easy win there.
- **The grad return could be fused with nothing** — but note PPGD sends g_CI peer-to-peer
  immediately after backward (already optimized per the comment at `step_ppgd.py:122`).
The real lever is **F-DTYPE-2/F-DTYPE-1 first** (they reduce on-GPU bytes, which is the
profiled bottleneck), not the wire (NIC overlaps with compute via the dead-time prefetch).
Flag, don't over-invest.

### F-PACK-1 — `.contiguous()` + cast on every pack/unpack of activation-sized tensors
`portals.py:154-161` `_pack_sites`: `d[s][sub].detach().to(WIRE_DTYPE).contiguous().flatten()`
and the unpack `.copy_(view.to(fp32))` on recv. Each send/recv of a [256,S,1024] CI does a
cast + a contiguous copy (537 MB) on top of the NCCL transfer. Sub-slicing `d[s][sub]`
when `sub` is a non-trivial slice forces the `.contiguous()` copy. With n_per_block=1 /
coarse-CI the slices are usually whole-tensor (contiguous already) — but `.contiguous()`
on an already-contiguous tensor is a no-op, so the cost here is the **`.to(WIRE_DTYPE)`
cast** (bf16 from fp32 CI). If F-DTYPE-1/2 land (CI stays bf16), these casts vanish.

### F-UNUSED-1 — `pre_sigmoid` computed every CI step, used only in eval
`component_model.py:166-171`: `_ci_global` always splits `pre_s` into 96 tensors and
builds the `pre_sigmoid` dict. In training, only `lower_leaky` (send/bwd) and
`upper_leaky` (imp_min) are consumed; `pre_sigmoid` is dead. The split itself is cheap
(views), but it keeps the full `out` graph + 96 view tensors alive. Minor.
**Fix:** make `pre_sigmoid` lazy / skip in the train path (it's only needed by
`CiOutputsEvalToPPGD`). Low payoff; note for cleanup.

### F-CKPT-1 — PPGD warmup rebuilds the full masked forward graph N times, un-checkpointed
`persistent_pgd_state.py:344-351`: each of `n_warmup_steps`(=2) does a full masked forward
+ source-only backward, and PPGD has activation checkpointing **disabled**
(`optimize.py:276-277`). So PPGD does (2 warmup + 1 final) = 3 full [8,S,1600] forwards
per step, each holding full activations. At bl_pp=8 the per-rank activation is small
(~100 MB hidden), so this is tolerable, but it's 3× the forward FLOP of one pass and the
warmup graphs are discarded (`retain_graph=False`). Known per CLAUDE.md (ckpt is
LW-only because PPGD's nested mask_infos recompute is non-deterministic). Flag as the
PPGD compute-floor, not a quick fix.

### F-ORDER-1 — sequential per-seed backward through the 2.64B CI fn (diagnostic split)
`step_ci.py:375-380`: two `torch.autograd.backward` calls (g_total seeds, then imp) with
`retain_graph=True` on the first — explicitly a *diagnostic* split. It doubles graph
traversal bookkeeping vs a single fused backward. The docstring says it's for profiler
attribution. **Fix once diagnosis is done:** collapse to one
`torch.autograd.backward(tensors=lower_leaky+[scaled_imp], grad_tensors=g_total+[None])`.
The CI-pool backward is ~70% of the CI step (per MEMORY), so any constant-factor on it
matters; retain_graph=True forces the graph to be kept through the first pass.

### F-SYNC-1 — fp32 `.grad` dest tensors allocated fresh every CI step
`portals.py:331-334, 390-393`: the CI recv allocates `out = {s: torch.empty(b_ci,S,C,
fp32)}` for both LW and PPGD grad receives → 2 × 3.22 GB fresh fp32 allocs/step, then
`copy_(...to(fp32))` per packet. Pairs with F-DTYPE-2: if grads stay bf16 end-to-end these
become bf16 (halved) and the per-packet upcast disappears. Allocation churn also pressures
the caching allocator. **Fix:** reuse a persistent fp32 (or bf16) buffer across steps, or
keep bf16.

## Summary of top levers

1. **F-DTYPE-2** (drop fp32 re-leaf of CI on LW+PPGD) — kills the largest fp32
   activation allocs (1.07 GB/site LW, 3.22 GB PPGD) and the fp32 mask arithmetic that
   dominates the profile.
2. **F-DTYPE-1** (drop fp32 upcast of H cache) — removes a 5–10 GB fp32 concat/cast on the
   CI critical path.
3. **F-MASK-1** (fuse + bf16 the `ci+(1-ci)u` mask synthesis) — collapses 3 act-sized
   passes into 1; depends on F-DTYPE-2.
4. **F-DELTA-1** (compute weight-delta once per step, not per-site/twice) — removes
   redundant fp32 GEMM+subtract on LW.

All four attack on-GPU bandwidth/cast, which the profiler said is the bottleneck — not the
wire (which overlaps via the prefetch). Each fp32→bf16 change must be validated with an
RNG-pinned one-backward grad check, not loss-curve equivalence.
