Scaling SPD beyond DDP

An FSDP feasibility report — what works, what breaks, and what to do first.

Drafted from a read of param_decomp/ at main. References are file:line against the working tree.

TL;DR

Yes, FSDP is the right next step — but it's not a drop-in replacement for the current DDP wrapper, and it's not the cheapest first move. SPD has three architectural quirks that interact badly with naive FSDP wrapping: (i) a frozen target model that gets read repeatedly per step, (ii) a forward-hook system that runs components[name](x) from inside a hook on a different module than where the components' parameters live, and (iii) calc_weight_deltas(), which reads full target and component weights once per step. The cheapest substantial win is almost certainly ZeRO-1 (optimizer-state sharding) + gradient checkpointing on the CI transformer and the target's transformer blocks. Real FSDP should come second, and only after we've decided how to handle the hook/weight-delta interaction. Concrete plan in §8.

1. Where distributed training currently lives

The codebase already has a small but real distributed scaffolding. It is uniformly DDP-based — there is no FSDP code anywhere in param_decomp/. The relevant pieces:

  • Process-group bootstrap: param_decomp/utils/distributed_utils.py. init_distributed() picks nccl on CUDA, gloo on CPU, reads RANK/WORLD_SIZE/LOCAL_RANK from env (set by torchrun). Wrappers exist for all_reduce, broadcast_tensor, sync_across_processes, gather_all_tensors.
  • DDP wrap: run_param_decomp.py:164–184. The entire ComponentModel (which itself contains the frozen target model + components + CI fn) is wrapped in DistributedDataParallel. find_unused_parameters is not set. 
    wrapped_model = torch.nn.parallel.DistributedDataParallel(
    model, device_ids=[device_id], output_device=device_id,
)
  • The "always-call-the-wrapped-model-once" hack: run_param_decomp.py:268–272. Because some forwards in compute_losses only touch a subset of the parameters, the loop forces a call to wrapped_model(...) every step purely to make DDP register every parameter as participating. That comment is worth reading — it's a load-bearing line.
  • Data sharding: data.py:167–250. Streaming HF datasets use dataset.shard(num_shards=world_size, index=rank); non-streaming uses DistributedSampler.
  • Per-rank seed divergence: run_param_decomp.py:162, implemented in distributed_utils.py:259–271. Each rank gets seed * world_size + rank so stochastic masks differ across ranks. With DDP this is fine: backward all-reduces gradients, so each rank contributes a different mask sample to the average. Same will be true under FSDP.
  • Persistent PGD has its own reduction: persistent_pgd.py:138, 168–169, 177–181. PPGD sources aren't model parameters, so DDP doesn't sync them — there's an explicit all_reduce(op=AVG) for cross-rank scopes, and a deliberate skip for PerBatchPerPositionScope. This is independent of DDP/FSDP.
  • Launch path:
    • pd-local --dp N → scripts/run_local.py:47–58 shells out to torchrun --standalone --nproc_per_node=N.
    • pd-run (SLURM) → utils/compute_utils.py:99–128. Single-node uses standalone torchrun; multi-node uses srun + torchrun with rendezvous on the first allocated host.

So today the picture is: one process per GPU, one full replica of the (target + components + CI fn + AdamW state) on every GPU, gradient sync at backward. Standard.

Your "4× target" intuition

It's a fair gloss, though the breakdown matters for FSDP planning: ~1.3× from components, ~1.7× from the CI transformer, plus ~1× for the still-resident frozen target. The CI transformer and the components have very different sharding profiles — they're not the same problem.

3. From per-rank state to batch sizes

The per-rank state in §2 is what's fixed — it doesn't depend on batch size. Activations are what scale with batch. So GPU memory minus fixed state minus a workspace margin gives you the activation budget, which divided by per-batch-element activation cost gives you achievable batch.

The fixed-state formula

Let T = trainable params (components + CI fn), F = frozen target params, N = world size. Assuming fp32 master weights, fp32 grads, fp32 AdamW state — which is what Jose currently uses, despite autocast_bf16=True (autocast affects activations, not optimizer state):

DDP:    16·T + 4·F                     bytes per rank
ZeRO-1: (8 + 8/N)·T + 4·F              bytes per rank
FSDP:  ~16·T/N + 4·F/N                 bytes per rank   (full sharding, approx)

ZeRO-1's saving is 8·T·(N−1)/N per rank — linear in T, asymptoting to 8·T as N→∞. The absolute saving grows with model size, which is the regime we care about.

Fixed state at various scales

Assuming Jose's ratios hold (components ≈ 1.3× target, CI fn ≈ 1.7× target → trainable ≈ 3× target):

Anything above the GPU's memory size — assume 80 GB H100 — won't even start training under that strategy. DDP hits the wall at ~1.5B target; ZeRO-1 buys roughly another 2× before it runs out.

Translating to batch size

Activation memory depends on per-step forward count, autograd retention from PPGD warmup, and gradient checkpointing — there's no clean closed form. So I calibrate against an observed config:

Jose runs at batch_size: 64 on 80 GB H100s. With ~13 GB fixed state under DDP, that leaves ~67 GB for activations and workspace. So ~1 GB per batch element at Jose scale.

Activations scale roughly with d_model × n_layers × seq_len; parameters scale roughly with d_model² × n_layers. So activation/B grows roughly as √(target_params) under width scaling. Working assumption: activation/B ≈ 1 GB × √(target / 250 M).

Confidence

±50% on the activation-per-batch-element estimate, ±10% on the fixed-state figures (which are tight algebra). The headline batch numbers below should be read as order-of-magnitude, not exact. The investigation plan in the repo root specifies how to replace these with measured numbers.

Headline interpretation

  • Jose scale (~250M target): ZeRO-1 buys ~+5 batch/rank. We're not memory-bound here — this is mostly free headroom for future experiments.
  • 500M–1B target: ZeRO-1 + checkpointing is the difference between "uncomfortable" and "comfortable." At 1B specifically, batch 7 → batch 25 with both is a real productivity win.
  • 2B target: ZeRO-1 + checkpointing is the difference between doesn't fit at all and "fits at batch ~6." Qualitative — and ZeRO-1 alone is barely enough.
  • 4B+: ZeRO-1 is insufficient regardless. You need actual parameter sharding — i.e. FSDP. This is where Phase 2 of the plan starts paying off.

4. Why DDP runs out

You had this right but the shape isn't exponential. Two separate things break:

  1. Memory wall, not gradual decay. DDP per-rank memory is roughly constant in world size: every GPU holds a full (params + grads + optimizer state) replica. Adding GPUs only adds batch capacity; per-rank fixed cost doesn't drop. When the fixed cost crosses GPU memory, max-batch goes from "constant" to "zero" — a cliff, not a curve.
  2. Communication scaling, gradual. All-reduce time is O(P) where P is parameter count, independent of world size on ring all-reduce — but SPD already does many forwards per step (§6), and in DDP the all-reduce only fires once at backward(). So this is currently not the bottleneck.

The cliff is what bites. Extrapolating Jose to ~1B target with the same component:target ratio:

ComponentJoseHypothetical 1B target
Target (frozen)0.24 B1.0 B
Components0.32 B~1.3 B
CI fn (assume similar scaling)0.40 B~1.6 B
Trainable0.72 B~2.9 B

~50 GB of replicated training state on a 80 GB H100 leaves enough headroom for activations only with aggressive gradient checkpointing and bf16 throughout — and any larger and we're done. So your timing instinct is right: this is the regime where sharding stops being optional.

5. Three SPD-specific things any sharding strategy has to coexist with

5a. The target model is frozen but read constantly

run_param_decomp.py:147: target_model.requires_grad_(False), asserted at component_model.py:121–125. Target params have no grads and no optimizer state, so the only memory they cost is the parameter tensors themselves. But they are read every step in three places:

  1. The "target-only" forward at run_param_decomp.py:272 for input caching and KL targets.
  2. Inside every component-replacement forward, the original target module runs first and the hook fires after (see 5b).
  3. calc_weight_deltas() at run_param_decomp.py:263, which reads the full .weight of each decomposed target submodule.

If we shard the target with FSDP, every one of these reads triggers all-gather, and per-step we'll do that 5–10 times. That's a lot of unnecessary comm for parameters that never change. Strong preference: don't shard the frozen target unless we have to. Shard only the trainable parts. This implies non-uniform FSDP wrap policy.

5b. Components live in a separate ModuleDict, not on the target submodules

This is the architectural decision that makes FSDP wrapping hard.

From component_model.py:131–137:

self.components = ComponentModel._create_components(target_model=target_model, module_to_c=...)
self._components = nn.ModuleDict(
    {k.replace(".", "-"): self.components[k] for k in sorted(self.components)}
)

Forward replacement is implemented as a forward hook registered on the target submodule (component_model.py:489–501). The hook closure calls components[module_name](x, mask=...) — which dispatches into a parameter tensor that lives in self._components, a sibling tree.

# component_model.py:457-481 (slightly abridged)
if components is not None and mask_info is not None:
    components_out = components(x, mask=..., weight_delta_and_mask=...)
    final_out = components_out if mask_info.routing_mask == "all" else \
                torch.where(mask_info.routing_mask[..., None], components_out, output)
    return final_out

What this means under FSDP: the target submodule runs (its FSDP unit gathers, computes, optionally frees), then the post-forward hook runs and tries to dispatch into another FSDP unit (the components for that module). FSDP's auto-wrap policy will not have prefetched the components' shard, so the hook either incurs an extra all-gather right there or fails outright. The hook crosses FSDP unit boundaries.

There are three plausible fixes, ranked by invasiveness:

  1. Fuse target submodule + its components + its CI piece into a single nn.Module per decomposed site, and FSDP-wrap that fused unit. Conceptually clean, eliminates the cross-unit access, but is a meaningful refactor of ComponentModel.
  2. Manually summon_full_params(components_for_this_module) inside the hook. Works but is comm-heavy and sequential; defeats most of FSDP's benefit because we're round-tripping inside hot path.
  3. Don't shard components (only shard the CI transformer + target). Components are ~323M for Jose, ~1.3B at the 1B-target scale. At the 1B scale that's too big to leave unsharded. So this only works for a transitional intermediate scale.

Option 1 is the right destination, in my view. It also generalises: a "decomposition site" becomes a real first-class object, which has knock-on benefits for harvest, attribution, autointerp.

5c. calc_weight_deltas wants the full weights, materialized

component_model.py:646–651:

def calc_weight_deltas(self) -> dict[str, Float[Tensor, "d_out d_in"]]:
    weight_deltas = {}
    for comp_name, components in self.components.items():
        weight_deltas[comp_name] = self.target_weight(comp_name) - components.weight
    return weight_deltas

Where components.weight is the property at components.py:430–432:

@property
def weight(self) -> Float[Tensor, "d_out d_in"]:
    """(V @ U).T."""
    return einops.einsum(self.V, self.U, "d_in C, C d_out -> d_out d_in")

Two issues:

  1. This is called once every step (run_param_decomp.py:263) when use_delta_component=True — which is on in the Jose config. It materializes the full (d_out, d_in) delta for every decomposed module, and that delta then participates in the forward (components.py:469–475: x @ weight_delta).
  2. Under FSDP both V, U, and the target .weight are sharded. Reading self.V in a sharded FSDP unit returns the local shard, not the gathered tensor. Without a summon_full_params wrapper, einsum(V, U, ...) is silently wrong (or it crashes due to shape mismatch — depends on the FSDP version and wrap policy).

This needs deliberate handling. Options, in order of preference:

  1. Do the delta computation inside the hook, after summon_full_params has been done by FSDP's own forward path — which is automatic if components are part of the same FSDP unit as their target submodule (the option-1 fusion above).
  2. If we keep the explicit calc_weight_deltas call at the top of the step, wrap it in FSDP.summon_full_params(component_model, recurse=True, writeback=False). Cheap to write but pays a full-gather on every step.
  3. Reformulate so the delta is never materialized: x @ (W_target − V@U) = x @ W_target − (x @ V) @ U. Both halves can be computed without ever forming the (d_out, d_in) delta tensor. This is a strict win even ignoring FSDP — we save an O(d_in · d_out) materialization in favor of two O(batch · seq · d) matmuls — and it removes the need for calc_weight_deltas at the top of the step entirely. This is probably worth doing independently.

6. Specific FSDP friction points, with line numbers

If we tried to swap DistributedDataParallel(model) for FSDP(model, auto_wrap_policy=...) tomorrow, here is the list of everything that will break or behave oddly. Worth keeping as a checklist.

SiteWhat goes wrongFix shape
run_param_decomp.py:172 — DDP(model) Direct replacement is wrong. FSDP wants per-block wrapping, not whole-model wrapping, to actually shard parameters and not just the outer module. Custom auto_wrap_policy: wrap each target transformer block, each CI transformer block, and each LinearComponents as separate FSDP units (or fuse, see §5b).
run_param_decomp.py:263 — calc_weight_deltas() Reads sharded V, U, and target .weight outside any forward. Either silently wrong or crashes. Reformulate to never materialize (d_out, d_in) delta (see §5c option 3).
component_model.py:175–187 — target_weight() Returns target_module.weight directly. Sharded under FSDP. Either fuse target submodule + components into one FSDP unit, or wrap callsites in summon_full_params.
component_model.py:457–481 — forward hook calls components[name](x) Cross-FSDP-unit dispatch from a hook. Components' params not gathered when hook fires. Fuse target submodule + components into a single FSDP unit (§5b option 1), so FSDP's own pre-forward hook has already gathered them.
run_param_decomp.py:268–272 — "must call wrapped_model once" hack This is a DDP-ism (DDP requires forward to touch every parameter). FSDP doesn't have this constraint. Currently harmless but vestigial; might mask a real bug if it papers over a missing forward elsewhere. Remove under FSDP. Verify nothing else relied on it.
run_param_decomp.py:198–207 — optimizer params list Manually concatenates component_params + ci_fn_params. AdamW(optimized_params, ...) still works because FSDP returns FlatParameters that look like nn.Parameter, but the per-group LR/clip logic needs auditing. Tied weights (run_param_decomp.py:186–196) FSDP doesn't support cross-FSDP-unit tying; it flattens parameters per unit. Either keep tied weights inside one FSDP unit, or replace with a re-tying step at forward time.

How many forwards per step actually happen?

Counting the Jose config (pile_llama_simple_mlp-4L.yaml):

  1. 1× target-only forward with input caching (run_param_decomp.py:272).
  2. 1× CI-fn forward on cached activations (small).
  3. 2× component forward + backward for PPGD warmup (n_warmup_steps: 2, run_param_decomp.py:281).
  4. 3 active reconstruction-style losses in compute_losses — StochasticReconSubsetLoss, PersistentPGDReconLoss, FaithfulnessLoss — each driving one component forward at n_mask_samples=1. Plus ImportanceMinimalityLoss, which uses CI directly.

Total: roughly 5–7 component forwards + 2–3 backwards per training step, which is the load FSDP's all-gather has to absorb. This is high but not crazy. Prefetching should hide most of it.

7. Cheaper levers worth pulling first (or alongside)

FSDP is a real refactor. Several things give large memory wins for far less work and stack well with FSDP later.

7a. ZeRO-1 (ZeroRedundancyOptimizer)

Drop-in replacement for AdamW at run_param_decomp.py:207 — shards optimizer state across ranks, leaves params and grads replicated. For Jose: optimizer state is 5.78 GB out of 12.6 GB per-rank state, so ZeRO-1 across 4 ranks frees ~4.3 GB/rank. Across 8 ranks, ~5.0 GB/rank. Smallest possible code change, ~30–40% memory recovered.

from torch.distributed.optim import ZeroRedundancyOptimizer
optimizer = ZeroRedundancyOptimizer(
    optimized_params, optimizer_class=optim.AdamW,
    lr=config.lr_schedule.start_val, weight_decay=0,
)

Caveats: per-param-group hyperparameters (you have two: components and ci_fn) need to be set after construction. Save/load needs consolidate_state_dict().

7b. Gradient checkpointing on the CI transformer and the target's transformer blocks

The CI transformer is the single biggest activation consumer per forward (it's a full transformer over batch×seq). Checkpointing its blocks ~halves activation memory. The target's transformer blocks are run multiple times per step → checkpointing them halves memory but doubles compute on those forwards. Likely still net positive on memory-bound runs.

Implementation: use torch.utils.checkpoint.checkpoint_sequential on the block list, or apply at construction time inside GlobalSharedTransformerCiFn and the target's LlamaSimpleMLP. Doesn't touch the SPD machinery at all.

7c. bf16 master weights

Currently autocast_bf16=True, but master weights and AdamW state are fp32. Switching to bf16 master + fp32 Adam state gives ~halving of param/grad memory. Not always stable for SPD given the loss landscape; needs careful testing on a small target before committing. Lower-priority than 6a/6b.

7d. Stop materializing weight_delta

From §5c: rewrite x @ (W_target − components.weight) as x @ W_target − (x @ V) @ U. Saves an O(d_in · d_out) materialization per decomposed module per step. For Jose, that's ~10 modules × 16M floats × 2 bytes ≈ 320 MB of intermediate state that doesn't have to exist. And it removes the trickiest FSDP hazard from calc_weight_deltas. Pure win even before sharding.

7e. CPU offload for the frozen target's optimizer state

Trivially: there is none. So this doesn't apply. Mentioned for completeness.

What's NOT going to help meaningfully

  • Tensor parallelism (TP/Megatron-style): Helpful when a single matmul exceeds GPU memory or when activations dominate. We're parameter-state-dominated. Skip.
  • Pipeline parallelism: Worth considering at >10B target model. Not now.
  • Sequence parallelism: Useful at long contexts. Jose is 512. Not now.

8. Recommended phased plan

Recommendation

Three phases. Phase 1 alone might be enough to get to a 1B target on 8×80GB. Phase 2 buys the next 2–3× of headroom. Phase 3 is the architectural commitment.

Phase 1 — quick wins, ~1–2 weeks of work

  1. Profile current memory. Run Jose at batch 64 on 1×H100 with torch.cuda.memory._record_memory_history + torch.cuda.memory_summary. Identify the actual top-3 allocators. Don't skip this. The whole plan below assumes the per-rank breakdown I estimated; it could be wrong.
  2. Switch optimizer to ZeroRedundancyOptimizer behind a config flag. Verify save/load round-trips with consolidate_state_dict.
  3. Add gradient checkpointing to the CI transformer (GlobalSharedTransformerCiFn) and to the target's transformer blocks. Config-flag it.
  4. Rewrite the weight-delta path to never materialize the (d_out, d_in) delta. Remove the per-step calc_weight_deltas call entirely; do the equivalent two-matmul form inside LinearComponents.forward when weight_delta_and_mask is requested.

Exit criterion: Jose runs at the same batch size on a 40 GB A100, or at 2× batch on an 80 GB H100. (Pick whichever is more useful.)

Phase 2 — fuse the decomposition site, then FSDP, ~3–4 weeks

  1. Refactor ComponentModel so each decomposed module + its components forms a single nn.Module. Concretely: a DecomposedLinear module that wraps the original nn.Linear as a child, holds V, U, bias as its own parameters, and replaces the target's nn.Linear in the model tree (instead of adding a hook on it). This eliminates the cross-FSDP-unit access pattern entirely. It's the same forward semantics, just expressed structurally instead of via hooks.

    This is a bigger change than it sounds, because hooks are how the codebase currently does input/output/component-act caching too. The replacement needs to expose those caches as well. But it's the change that unlocks everything else, and arguably it's better factoring even without FSDP — the current hook-based scheme is a bit of an "action at a distance" pattern.

  2. Wrap with FSDP using a custom auto_wrap_policy. One FSDP unit per DecomposedLinear, one per CI-transformer block, one per target transformer block. Don't outer-wrap the whole model. Set forward_prefetch=True, backward_prefetch=BACKWARD_PRE.
  3. Replace DDP-specific bits: FSDP.clip_grad_norm_, FSDP.state_dict_type for save/load, drop the "must-call-wrapped_model" line at run_param_decomp.py:268–272.
  4. Decide on the frozen target. Options:
    • Don't shard it — leaves it replicated, costs ~1 GB/rank for Jose, ~4 GB/rank at 1B target. Avoids per-step all-gather of frozen weights. Probably the right default.
    • Shard it with NO_SHARD-policy FSDP units — gives sharding without the runtime gather (parameters stay sharded but live on each rank's slice). Useful if even the frozen target is too big.

Exit criterion: 1B-target run completes on 8×80GB H100 at meaningful batch size with throughput within ~1.7× of an equivalent DDP run (FSDP overhead is real).

Phase 3 — only if Phase 2 isn't enough, >1 month

  1. Move CI-fn to a separate process group. The CI transformer is conceptually independent from the components — it's reading cached target activations and producing CI scores. There's a case for putting it on its own subset of GPUs with its own pipeline.
  2. Tensor parallelism on the CI transformer's MLPs and attention, if it's still the bottleneck after FSDP.
  3. Activation offload to CPU. Last resort.

9. Open questions and things I couldn't verify in this pass

  1. Is the target really ~242M or are MLPs gated (SwiGLU)? LlamaSimpleMLP is named "simple" specifically to avoid that, but worth confirming on the actual checkpoint. Affects parameter math, not the plan.
  2. Are embeddings tied? If yes, the ~41M embedding figure is single-counted; if no, it's roughly doubled. Doesn't change the conclusion but affects the table.
  3. How much of the per-rank memory is actually activations vs param/grad/optimizer state? I assumed param/grad/opt dominates because of the mask-sample × multi-loss multiplier on activations. Phase 1 step 1 (profile) tells us for sure.
  4. Does PPGD warmup work cleanly under FSDP? It does torch.autograd.grad(loss, list(self.sources.values())) at persistent_pgd.py:175. The sources aren't model params and shouldn't be FSDP-managed, so this should be fine — but the loss computation does flow through FSDP-wrapped components, which means the autograd graph crosses FSDP boundaries. Worth a small test.
  5. Is the CI transformer always going to be ~the size of the target? It's a config knob (ci_config.simple_transformer_ci_cfg). For Jose it happens to be similarly sized; for a 1B target you might want a smaller CI fn. If so, the trainable-parameter math changes meaningfully.
  6. Tied weights interaction with FSDP. The Jose config doesn't appear to use tied_weights for components (the tied_weights mechanism at run_param_decomp.py:186–196 ties U↔V.T across components). If/when this is used, FSDP unit boundaries need to keep tied params together. Easy if the tied modules are in the same decomposed-block fusion, but worth flagging.
