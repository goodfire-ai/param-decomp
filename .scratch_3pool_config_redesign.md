# 3-pool topology config — redesign proposal

Goal: cut the topology block from ~200 lines of hand-written rank integers to ~5 meaningful
numbers; make invalid states unrepresentable; surface the info that actually drives decisions
(per-rank batch = memory; GPU count = budget).

## 1. What the current schema authors vs what's actually free

Current `runtime.topology` (`ThreePoolConfig`) authors:
- `ci_ranks: list[int]`        — explicit global rank ids
- `ppgd_ranks: list[int]`      — explicit global rank ids
- `layerwise_block_groups: [{ranks: list[int], owned_sites: list[str]}]`
- `use_fused_kl: bool`

Plus `runtime.dp: int` (world size) and the CLI `--dp N`.

**The rank integers carry no information.** Proof points in the code:
- `build_world` only needs the *partition* (which ranks group together) + a canonical order;
  it asserts `Σ ranks == world_size`, disjointness, uniform `n_per_block`.
- The rank-0 convention *requires* `layerwise_block_groups[0].ranks[0] == 0` — i.e. there's
  already a forced canonical ordering (LW blocks first).
- The committed b512 config assigns LW=0–31, CI=32–63, PPGD=64–95 — pure canonical order.
- Resume's `_rank_invariant_fingerprint_core` deliberately throws the rank lists away and keeps
  only `{world_size, n_ci, n_ppgd, n_blocks}`. The per-block ranks→sites mapping is *re-derived*.

So the genuine degrees of freedom are just:
1. `batch_size`                         — already on `pd`
2. CI pool parallelism                  — one number
3. PPGD pool parallelism                — one number
4. LW batch-parallelism per block       — one number (`n_per_block`, uniform)
5. LW site→block partition              — one number (`sites_per_block`) for the uniform case
6. `use_fused_kl`                        — bool

Everything else (rank ids, world size, owned_sites, block count) is **derivable**.

## 2. Redundancies / invalid-states the current schema permits

World size is specified **three times** and must agree: `--dp 96`, `runtime.dp: 96`, and the
96 explicit rank integers. (`runtime.dp` is then *overwritten* from the torchrun world anyway.)

`owned_sites` **duplicates** `pd.decomposition_targets` — the LW pool must own exactly the
decomposed sites; the only new info is how they're grouped. Coverage is checked by a runtime
validator that can mismatch.

Representable-but-invalid states the validators must catch at parse/runtime:
overlapping ranks · duplicate ranks · gaps in numbering · ranks ≠ world_size · non-uniform
`n_per_block` · rank-0 not block-0 leader · owned_sites not covering decomposition_targets ·
`n_ci`/`n_per_block`/`n_ppgd` not cross-divisible · batch not divisible by each arity.

**Every one of these vanishes if we stop authoring rank integers and derive them.**

## 3. Proposed schema

Author per-rank batch (the memory-meaningful number the whole topology discussion turned on),
not rank counts. GPU count becomes a derived readout.

```yaml
runtime:
  autocast_bf16: true
  topology:
    batch_size: 512          # global batch (single source of truth; see note)
    ci:    { per_rank_batch: 16 }      # → n_ci   = 512/16 = 32 replicas
    ppgd:  { per_rank_batch: 16 }      # → n_ppgd = 32
    layerwise:
      per_rank_batch: 16               # → n_per_block = 32 (DDP per block)
      sites_per_block: 3               # partition the decomposed sites in order
    use_fused_kl: true
```

Derived (all on the `World`, none authored):
- `n_ci = batch/16 = 32`, `n_ppgd = 32`, `n_per_block = 32`
- `n_blocks = ceil(n_decomposed_sites / sites_per_block)`  (1 for Llama-L18, 16 for GPT2-XL q/k)
- `world_size = n_blocks·n_per_block + n_ci + n_ppgd`  (96 for Llama, 224 for GPT2-XL)
- rank assignment = canonical order: block0 ranks, …, blockN ranks, CI ranks, PPGD ranks.
  ⇒ rank 0 is block-0 leader **by construction** (convention no longer needs a validator).
- `owned_sites` per block = positional slice of the expanded `pd.decomposition_targets`.

Llama-L18 topology in full becomes those 6 lines instead of ~110.

### What becomes unrepresentable (vs a validator)
- rank overlap / dup / gap / sum-mismatch — no rank ids exist to get wrong
- non-uniform `n_per_block` — it's a single int, not a per-block list
- rank-0 convention — canonical assignment guarantees it
- `owned_sites` ≠ decomposition_targets — derived by partitioning them, can't drift
- triple-specified world size — derived once, asserted == torchrun world

### What still needs a validator (irreducible arithmetic), but reads intuitively
- `batch_size % per_rank_batch == 0` for each pool (clean "bl must divide batch")
- cross-divisibility of the resulting arities (CI↔LW, CI↔PPGD). On per-rank batches this is
  "`bl_ci` and `bl_lw` cross-divide" — still one assert, but with a memory-grounded message.

## 4. Decision to make: per-rank-batch vs rank-count as the authored primitive

| | author `per_rank_batch` | author `dp` (rank count) |
|---|---|---|
| surfaces | memory driver (what you tune) | GPU budget (what you request) |
| derives | GPU count | per-rank batch |
| divisibility reads as | "bl divides batch" | "dp divides batch" |

Both are clean; they're inverses. Recommendation: **per_rank_batch** — the entire b512 sizing
exercise was "bl=16 fits, bl=32 OOMs"; memory is the binding constraint you actually reason
about, and GPU-count-as-output matches "how many nodes do I request." (Could expose the derived
`n_ci`/world_size in a logged summary + `__repr__` so the budget is still visible.)

## 5. Notes / edges
- **batch_size location.** Today it's `pd.batch_size`; topology divisibility validators live on
  the experiment config because they need both. If per_rank_batch moves to topology, either keep
  `batch_size` on `pd` and reference it, or move it into `topology` and have `pd` read it. Leaning
  keep on `pd` (it's an algorithm knob too) and validate in the experiment config as today.
- **Non-uniform site grouping** (e.g. isolate `down_proj`): not expressible via `sites_per_block`.
  YAGNI for current runs (uniform). Escape hatch: allow `layerwise.blocks: list[list[pattern]]`
  as an alternative to `sites_per_block` (still no ranks). Add only when wanted.
- **n_blocks needs pattern expansion** (`h.*.attn.q_proj` → 48 sites), which needs the loaded
  model — so `world_size` is finalized in `_build_runtime`, cross-checked against the torchrun
  world. Same place the site-coverage check already lives. Counts that don't need expansion
  (n_ci, n_ppgd, n_per_block, divisibility) still validate at parse time.
- **Resume fingerprint** simplifies: store the authored shape (ci/ppgd/block per_rank_batch +
  sites_per_block) — already rank-invariant, no special-casing.
- **Migration:** existing `ThreePoolConfig` (explicit ranks) is on-disk in p-b6505e9c etc. Per
  the no-legacy norm: new schema, regenerate configs; keep a one-shot reader for the old
  fingerprint only as long as a live run resumes from it (the existing TODO already scopes this).

## 6. Suggested implementation shape
- New `ThreePoolTopology` (replaces `ThreePoolConfig`): `ci`, `ppgd`, `layerwise`, `use_fused_kl`,
  each pool a tiny `PoolSpec(per_rank_batch: int)`; `layerwise` adds `sites_per_block` (or `blocks`).
- A pure `resolve_world_layout(topology, expanded_sites, batch_size) -> WorldLayout` that produces
  the canonical rank assignment + block→sites map (the thing `build_world` consumes). One place
  owns the canonical ordering; `build_world` loses its rank-list params and takes the layout.
- Drop `runtime.dp` as an authored field (derive; assert == torchrun world).
- Parse-time validators on the counts; expansion-dependent checks in `_build_runtime`.
