# ComponentModel redesign — feasibility assessment

READ-ONLY analysis. Goal: a ComponentModel whose target forward is a **pure
`nn.Module`** so it composes with activation checkpointing, FSDP, and
`torch.compile` — unblocking a larger LW per-rank batch (`bl_lw`) for the
batch-256 push.

## 1. Current mechanism (precise)

### Components are NOT structurally inside the target model

`ComponentModel.__init__` (`param_decomp/component_model.py:71-124`) builds the
components as a **side dict**, registered as a sibling `ModuleDict`, NOT swapped
into the target module tree:

- `self.components = make_components(target_model, self.module_to_c)`
  (`component_model.py:106`) → `dict[path, Components]`.
- `self._components = nn.ModuleDict({k.replace(".","-"): ...})`
  (`component_model.py:107-109`) — registered only so DDP/`.to()` see the params.
- The target model is stored untouched as `self.target_model`
  (`component_model.py:102`); its params are asserted frozen
  (`component_model.py:96-100`).

So the target tree and the component tree are **disjoint**. The components reach
into the target's data flow only at forward time, via hooks.

### Masking/routing delivery = forward hooks + a context manager

The whole injection lives in `ComponentModel.forward`
(`component_model.py:212-264`):

1. The caller passes `mask_infos: dict[path, ComponentsMaskInfo]` as an explicit
   forward arg (`component_model.py:216`). `ComponentsMaskInfo`
   (`masks.py:24-36`) bundles `component_mask [..., C]`, `routing_mask
   [...] | "all"`, and optional `weight_delta_and_mask`.
2. For each target path in `mask_infos`, it builds a `partial` of
   `_components_and_cache_hook` closing over that site's `Components`, its
   `mask_info`, the `cache_type`, and a shared mutable `cache` dict
   (`component_model.py:244-255`).
3. `_attach_forward_hooks` (`component_model.py:323-335`) registers each as a
   `register_forward_hook(hook, with_kwargs=True)` on the **target submodule**,
   runs `self._run_batch(self.target_model, batch)` inside the `with`
   (`component_model.py:257-258`), then removes the handles in `finally`.
4. The hook (`_components_and_cache_hook`, `component_model.py:266-321`) reads
   the module's input `x`, runs `components(x, mask=..., weight_delta_and_mask=...)`
   (`component_model.py:297-302`), and **returns a replacement output**, so the
   target Linear/Conv1D/Embedding's own output is discarded. Routing:
   `torch.where(routing_mask[...,None], components_out, output)`
   (`component_model.py:307-311`).

`Components.forward` itself (`components.py:129-165`) is pure given
`(x, mask, weight_delta_and_mask)`: `comp_acts = V^T x`; `(comp_acts * mask) @ U`;
`+ delta_mask * (Δ @ x)`; `+ bias`.

### Why `__call__` is impure

The impurity is **not** in `Components` and **not** in the `mask_infos` argument
(that's already threaded explicitly). It is that the masks are delivered to the
target submodules through a **side channel**: `register_forward_hook` mutates
global module state, and the hook's effect depends on enclosing-context state
(the `with self._attach_forward_hooks(...)` block, the shared `cache` dict). The
target model's `forward` therefore returns different things depending on whether
hooks are currently attached — its behavior is governed by side state set
outside its own call. That is the root blocker.

### CI fn flow (orthogonal, already mostly pure)

CI is computed separately: a `cache_type="input"` forward harvests
`pre_weight_acts` (the hook stashes `x` into `cache`, `component_model.py:288-289`),
then `calc_causal_importances` (`component_model.py:337-365`) runs `self.ci_fn`
on that dict and applies the leaky sigmoids. The CI fn (`ci_fns.py`) is a normal
`nn.Module` taking a dict of acts — it's already compile/FSDP-friendly. The only
hook dependency is **harvesting the inputs**, which a structural redesign
replaces with module-internal caching or a returned aux dict.

## 2. Why each scaling tool breaks

**(a) `torch.utils.checkpoint`.** Checkpoint reruns the wrapped forward during
backward with grad enabled. For correctness the recompute must be *identical* to
the original. The hook path puts the masking logic outside the checkpointed
function: the hook closes over a `mask_info` and a mutable `cache` dict
(`component_model.py:248-255`), and the replacement is keyed off whether handles
happen to be attached. On recompute, PyTorch reruns the inner `forward` but the
surrounding `with _attach_forward_hooks` is gone, the closure's RNG-derived masks
(continuous source draws happen *outside* in `calc_stochastic_component_mask_info`,
`masks.py:236-241`, so those are fixed) — but the per-call mutable `cache` writes
and the hook's output-replacement are exactly the kind of side effect checkpoint
documents as unsupported. You'd be checkpointing a function whose true output
depends on module-global hook state, so recompute is fragile/non-equivalent.

**(b) FSDP.** FSDP wraps modules, flattens their params into a `FlatParameter`,
and shards/all-gathers around `module.forward`. The components are NOT FSDP-wrapped
children of the target (they're a disjoint `ModuleDict`,
`component_model.py:107`), so the masked output is produced by `V/U` params that
FSDP, wrapping the target, never gathers in the target's forward. Worse, the hook
fires *inside* the wrapped target module's forward and reads `Components` params
that belong to a different FSDP unit — the all-gather/reshard lifecycle of the two
trees is uncoordinated. Hook-based output replacement on a sharded module is
exactly the pattern FSDP's pre/post-forward hooks fight with.

**(c) `torch.compile`.** Dynamo traces `module.forward`. `register_forward_hook`
that *returns a new output* is a side-effecting global-state mutation Dynamo
either can't capture or guards on weakly, forcing graph breaks at every hooked
module. The mutable `cache` dict writes (`component_model.py:289,305,314`) and the
`mask_info is None` / `routing_mask == "all"` Python branches
(`component_model.py:291,309`) become guards or breaks. The repo already learned
the per-call SDPA toggle breaks compile (`sdpa_strict.py:5-12`) and that compiling
the *CI fn* alone is a wash (memory note in MEMORY.md); the target-forward hook
path is strictly worse for Dynamo than the CI fn.

Note the LW pool is where this bites: `step_layerwise.py:356` does a full masked
target forward per site at `bl_lw`, and `_target_fwd` (`step_layerwise.py:161`)
does a full unmasked target forward — both at the LW per-rank batch. Activation-
checkpointing that target forward would raise `bl_lw`, fewer LW ranks, faster.
`strategy.context` (`loss_strategy.py:30-48`) is only an `lm_head` bypass today —
no act-ckpt is wired anywhere in the repo (confirmed: no `torch.utils.checkpoint`
usage outside docstrings).

## 3. Reference: nano-param-decomp

`nano_param_decomp/run.py` is the single-file sibling. It is **structurally
closer to option (A)** but still impure in the same way:

- `install_components` (`run.py:270-283`) **swaps each `nn.Linear` in place** for
  a `ComponentLinear` via `setattr(parent, attr, wrapper)` — the components ARE
  in the module tree. This is the structural win the main repo lacks.
- But `ComponentLinear.forward` (`run.py:247-267`) still reads **transient
  instance attributes** set per-step: `self.mode`, `self.mask`, `self.delta_mask`,
  `self.routing_mask` (`run.py:236-239`). They're written by `set_wrapper_masks`
  (`run.py:475-485`) and cleared by `clear_wrapper_masks` (`run.py:488-493`)
  around each forward (e.g. `stochastic_recon_loss`, `run.py:507-511`).
- Pre-weight acts are harvested by stashing `self.last_input = x.detach()` in
  "target" mode (`run.py:250`), read by `SPDModule.forward` (`run.py:673`).

So nano replaced *hooks* with *in-place module swap*, but kept *side-channel
attribute mutation* as the mask-delivery mechanism. That makes it FSDP-friendlier
(components are real children, DDP wraps `SPDModule`, `run.py:743`) but it is
**still not compile/checkpoint-pure**: the forward branches on mutable
`self.mode`/`self.mask`, and `clear_wrapper_masks` in a `finally` is the same
context-manager-style impurity. nano never claims to support ckpt/compile/FSDP —
its docstring explicitly excludes checkpointing (`run.py:38`).

**Takeaway:** nano proves the in-place swap half of option (A) is easy and works
with DDP. It does NOT solve the mask-delivery purity problem — it just relocated
it. The redesign must do the swap *and* fix delivery.

## 4. Design options

### Option A — dynamic per-module restructuring (Oli's lean)

Programmatically swap each target `nn.Linear`/`Conv1D`/`nn.Embedding` for a
`ComponentLinear`-style module holding `V/U` (+ frozen `W_target`, bias, and the
ability to compute `Δ = W_target − VU`). The resulting target tree is an ordinary
`nn.Module`. Masks delivered **purely** (see §5) — NOT via mutated attributes.

- **FSDP:** GOOD. Components are real children of the target tree; one wrapping
  policy covers them. `V/U` are the only trainable params, so FSDP shards exactly
  what trains. This is the configuration FSDP expects.
- **Act-ckpt:** GOOD, *if* masks arrive as forward args (§5(i)). Checkpoint a
  transformer block; recompute reruns `ComponentLinear.forward(x, mask=...)`
  deterministically because the mask is an input tensor, not module state.
  (Buffer/attribute delivery, §5(ii), reintroduces the recompute hazard.)
- **compile:** GOOD with arg-threaded masks; the forward is a static sequence of
  matmuls + one `torch.where` with no global side effects. The `routing_mask ==
  "all"` and `mask is None` branches should be collapsed (always pass a tensor)
  to avoid guards.
- **Generality across HF models:** GOOD. Swap is by module *type* at known paths
  (`make_components` already dispatches Linear/Conv1D/Embedding/Identity,
  `components.py:255-313`). Works for any HF model whose targets are those types
  — same constraint the repo already has.
- **The hard part:** delivering masks purely without rewriting each HF model's
  `forward` signature (which doesn't accept a `masks=` kwarg). See §5.
- **Effort/annoyance:** MEDIUM. The swap + Components reshaping is straightforward
  (nano shows it). Single-source-of-truth for the four cache modes and the
  CI-input harvest needs care. The genuinely fiddly bit is mask delivery to deeply
  nested swapped modules without a side channel.

### Option B — vendor per-model code (thread components+masks through model forward)

Rewrite each target model (e.g. the vendored `gpt2_simple.py`) so its own forward
natively takes `components` + `masks` and threads them down.

- **FSDP / act-ckpt / compile:** GOOD (fully pure, fully explicit — the ideal end
  state for the compiler).
- **Generality:** BAD. One bespoke rewrite per target model. The whole point of
  ComponentModel is "any HF-loadable model whose targets are Linear/Conv1D/
  Embedding" (CLAUDE.md). Vendoring throws that away and creates a maintenance
  fork per model.
- **Effort/annoyance:** HIGH per model, and recurring. Only justified if we
  permanently commit to one or two target architectures.

### Option C — hybrid: structural swap (A) + a thin pure delivery shim

Swap modules as in (A), and deliver masks by **temporarily setting a buffer on
each ComponentLinear for the duration of one pure forward**, where the *forward
reads the buffer but the module is otherwise pure*, OR by a functional-call style
(`torch.func.functional_call` / passing masks via a per-forward immutable
mapping captured at swap time). This is "A with the least-invasive delivery."

- The viable hybrid is **A + buffer-delivery for the inner modules, but make
  delivery a single explicit step outside the checkpointed region** so recompute
  sees stable buffers. This is exactly the subtlety that determines ckpt
  correctness — see §5.

## 5. The crux: pure mask/routing delivery

The masks are per-(batch, pos, component) and differ across the several forwards
in one step (CI-masked, stochastic, PPGD-adversarial, unmasked, single-site LW).
The CI-fn output flows in as `ci` dicts that get interpolated with sources
(`mask = ci + (1-ci)*source`, `masks.py:241`). Hard cases to keep working:

- **Single-site LW recon** (`step_layerwise.py:351-356`): only ONE site masked,
  all others run as plain target Linear. Today: `mask_infos={site: ...}`, only
  that hook fires.
- **Δ-components**: `weight_delta_and_mask` adds `delta_mask * (Δ @ x)`
  (`components.py:154-160`); LW recomputes `Δ` per site (`step_layerwise.py:349`).
- **Stochastic + PPGD**: per-(b,pos,C) masks; PPGD masks carry grad back to the
  adversarial sources (`persistent_pgd_state.py`), so delivery must be
  autograd-transparent to the mask tensor.

Three delivery mechanisms:

**(i) Thread `masks` through `forward(x, *, masks)` down the call chain.**
- Purest; best for compile + ckpt + FSDP. But HF model forwards don't take a
  `masks` kwarg, so this is option (B) unless you intercept at the swapped-module
  boundary. Verdict: ideal numerically, impractical generically without rewriting
  model forwards.

**(ii) Per-step set masks as attributes/buffers on the swapped modules, then a
pure forward reads them.** This is nano's approach (`run.py:475-485`) and the
path of least resistance.
- **compile:** OK-ish if the buffer is a registered buffer of a stable shape
  Dynamo guards on; but per-step *reassignment* of a Python attribute (nano's
  `self.mask = ...`) triggers recompilation/guards. Registered-buffer `copy_` is
  safer than attribute rebind.
- **act-ckpt:** DANGEROUS unless the buffer set happens *outside* and *before* the
  checkpointed region and is not mutated between fwd and recompute. If you set the
  mask, enter checkpoint, and the mask survives unchanged into the recompute, it's
  correct. If anything clears it (a `finally: clear_wrapper_masks`) before
  backward, recompute reads a wrong/None mask. So buffer delivery + checkpoint can
  work but the lifecycle is the entire ballgame.
- **FSDP:** fine (buffers ride along).

**(iii) Restructure so masks are module-internal** (e.g. the swapped module owns
its CI sub-fn and computes its own mask). Wrong factorization here — CI is global/
shared across sites (`GlobalSharedTransformerCiFn`), and masks are sampled/adversarial
at the step level, not per-module. Reject.

### Recommended delivery: A + a **registered mask buffer set as one explicit,
checkpoint-stable step**, with masks as real autograd tensors

Concretely:

1. **Swap** each target module for `ComponentLinear`/`ComponentEmbedding`
   (in-place `setattr`, as nano `run.py:281`). Keep `W_target`, bias as frozen
   buffers; `V/U` as the only params. Result: pure target tree.
2. The swapped module's `forward(x)` reads a per-module mask **buffer**
   `self._active_mask` (and `_active_delta_mask`, `_active_routing`) and computes
   the masked output — *no Python-attribute rebinding*; use `buffer.copy_` /
   assign a tensor reference once per step via a single setter.
   - For sites NOT being masked this step (LW single-site case), the module
     forward must fall through to `F.linear(x, W_target)`. Encode that as a
     per-module boolean buffer / a sentinel mask of all-ones with
     `routing="target"`, chosen *once* before the forward — NOT branched on
     mutable Python state inside the traced region. Cleanest: a module-level
     `enabled` flag set at swap-config time per forward-kind, so each compiled
     graph variant is stable.
3. **Mask tensors carry grad** (they're `ci + (1-ci)*source`), so set them as
   plain tensor attributes the forward multiplies in — registered *buffers* break
   autograd to `source`/CI fn. Resolution: the mask is delivered as a **tensor
   attribute the autograd graph flows through**, but its *presence/shape* is what
   compile guards on, and it is set exactly once per forward and never cleared
   until after backward. (This is the one real tension: compile/ckpt want stable
   module state; autograd wants the mask to be a live graph tensor. A live tensor
   attribute satisfies both as long as it is not rebound mid-fwd↔bwd.)
4. **CI-input harvest** becomes module-internal: in "collect" mode the swapped
   module stashes `x` to an output aux dict (returned, not hooked) OR the CI fn
   reads acts captured by a single pure pre-forward. Prefer returning acts from a
   dedicated collect-forward so nothing is hidden.
5. Delete the hook machinery (`_components_and_cache_hook`,
   `_attach_forward_hooks`, the `cache_type` matrix) and replace the four cache
   modes with explicit return values.

This keeps the explicit top-level `mask_infos` contract the loss metrics already
use (`ci_masked_recon.py:27-28`, etc.) — only the *delivery from ComponentModel to
the submodules* changes from hooks to in-tree modules reading a once-per-step set
tensor.

## 6. Recommendation

**Option A (dynamic in-place restructuring), with delivery mechanism §5 above.**
Reject B (kills generality, recurring per-model cost) and pure (iii). A gives the
FSDP/ckpt/compile wins while preserving "any HF model with Linear/Conv1D/Embedding
targets." nano already demonstrates the swap is cheap and DDP-clean; the *new*
work vs nano is making delivery pure enough for ckpt/compile (nano's mutable
`self.mode`/`self.mask` is not).

Verdict table:

| Option | FSDP | act-ckpt | compile | generality | effort |
|---|---|---|---|---|---|
| A (swap + pure delivery) | GOOD | GOOD (arg/stable-tensor) | GOOD (collapse branches) | GOOD | MEDIUM |
| B (vendor per model) | GOOD | GOOD | GOOD | BAD | HIGH (recurring) |
| C (A + buffer shim) | GOOD | conditional on lifecycle | conditional | GOOD | MEDIUM |
| status quo (hooks) | BAD | BROKEN | BREAKS | GOOD | — |

## 7. Trickiest sub-problems to derisk first (in order)

1. **Mask-as-live-tensor vs compile/ckpt-stable-state tension** (§5 step 3). The
   mask must stay a graph tensor (grad to PPGD sources + CI fn) yet not be rebound
   between forward and checkpoint-recompute. Build a 1-layer toy: swap one Linear,
   checkpoint it, verify `torch.autograd.grad(loss, source)` matches the
   non-checkpointed path bit-for-bit (the repo's hard-won lesson: validate grad
   *scaling* with a real one-backward grad check, not loss curves —
   MEMORY.md `feedback_grad_scaling_needs_real_grad_check`).
2. **Single-site LW masking without a mutable branch** (`step_layerwise.py:356`).
   Decide the "this site masked, others target" encoding so each forward-kind is a
   *stable* graph (no Python branch on mutable state inside the compiled region).
   This is the LW pole — the actual motivation — so derisk it early.
3. **CI-input harvest without hooks.** Replace `cache_type="input"`
   (`component_model.py:288-289`) with an explicit collect-forward returning the
   per-site `pre_weight_acts` dict. Confirm the global CI fn still gets exactly the
   same acts (esp. embedding token-id → `V[x]` path, `ci_fns.py:524-528`).
4. **FSDP wrapping policy + 3-pool `drop_ci_fn`/`drop_components`.** The 3-pool
   pools delete one tree post-init (`optimize.py:260-266`); confirm an FSDP-wrapped
   swapped model still supports those drops and the LW pool can FSDP just the
   target+V/U while CI pool FSDPs just the CI fn.
5. **Δ-component under checkpoint** (`components.py:154-160`): `Δ = W_target − VU`
   depends on live `V/U`; under recompute it's recomputed from current params —
   fine, but confirm no stale `Δ` is cached across fwd/bwd.

## Uncertainty / honesty notes

- I have **not** prototyped the ckpt-recompute grad equivalence; sub-problem #1 is
  a genuine open question, not a known-good pattern. The autograd-tensor-as-module-
  attribute approach is the standard escape but its interaction with
  `torch.utils.checkpoint`'s recompute + Dynamo guards needs the toy in #1.
- Whether `torch.compile` gives a real LW speedup is unproven here — MEMORY.md
  records compile on the *CI fn* was a wash. The compile *compatibility* of option
  A is what matters for not foreclosing it; the act-ckpt win (raising `bl_lw`) is
  the concrete, separately-bankable payoff and does not require compile.
- FSDP integration with the bespoke 3-pool process-group topology
  (`three_pool/layout.py`) is plausible but unverified — 3-pool already manages its
  own groups; FSDP over a sub-pool is an additional layer I'd derisk only after
  single-pool A works.
