### Automated component labeling {toc: Automated labeling}

<label id="app:autointerp"/>

The component labels used throughout this paper were generated by prompting an LLM with per-component evidence harvested from the target model. We describe the procedure here for reproducibility; full source code is in `spd/autointerp/`.

**Evidence collection.** For each parameter component, we run a forward-pass harvest over the training distribution and record (i) the firing density of the component, (ii) a random sample of *activating examples* (token windows in which the component's causal importance exceeds a threshold $\tau_{\text{ci}} = 0.1$), and (iii) per-token co-occurrence statistics for *input* tokens (the token at the firing position) and *output* tokens (the model's next-token distribution at the firing position). Each activating example is a window of $20$ tokens of context on either side of the firing position ($41$ tokens total), truncated at sequence boundaries. We sample up to $30$ activating examples per component. From the harvested per-token statistics we compute, for both the input and output channels, top-recall tokens (the most common tokens conditional on firing) and top-PMI tokens (the same data normalized by base rate, in nats).

**Prompt.** For each component we construct a single prompt containing:

1. A short description of VPD: each weight matrix is decomposed into rank-1 subcomponents under faithfulness, minimality, and reconstruction losses, with an auxiliary causal-importance network producing the per-token mask values.
2. A note distinguishing *causal importance* (CI, the mask value, which is what we care about) from *inner activation* (the dot product of the input with the read direction $V$, scaled by the write-direction norm). The prompt instructs the labeler to weight CI heavily and treat low-CI/high-act positions as background.
3. A note on the sign convention: negating both $\vec{u_c}$ and $\vec{v_c}$ leaves the rank-1 matrix unchanged, so the absolute sign of the inner activation is arbitrary, but the *relative* sign within a component is meaningful (positive- and negative-act clusters can correspond to two distinct roles).
4. The component's layer ("MLP up-projection in the 2nd of 4 blocks", etc.) and firing density.
5. The top-recall and top-PMI tables for output and input tokens.
6. The $30$ activating examples, each rendered as an XML block with two views: a `<raw>` block of the literal token text, and an `<annotated>` block in which every firing token in the window is wrapped as `[[[token (ci:X, act:Y)]]]` (consecutive firings are grouped). Annotations are shown only for firing positions, since CI and act are noisy on non-firing tokens.
7. The task: return a structured-JSON object with a `label` of at most $8$ words and a `reasoning` summary. Only the label has a hard length cap; the reasoning field is asked to be "a short summary" with no specific length, bounded in practice only by the $8000$-token response budget. The instructions explicitly request epistemic honesty when the evidence is weak or mixed, and that different components should be described differently (some by input pattern, some by promoted output tokens, some by context, some by what they *don't* fire on).

**Model and decoding.** All labels were produced by `google/gemini-3.1-pro-preview` <cite>gemini3</cite> at `reasoning_effort=medium`, accessed through the OpenRouter API. The model was queried with structured-JSON outputs enforced via a `response_schema` constraint, with a maximum of $8000$ response tokens per call. Calls were issued in parallel with retry-on-rate-limit; failed calls (the rate of which we required to remain under $20\%$) were skipped rather than retried indefinitely.

**Coverage.** We labeled the $10{,}000$ components with the highest firing density on the harvested distribution. This covers all components that fire often enough for the harvested sample of activating examples to be informative; components below this cutoff fire too rarely to support reliable labeling.

**Caveats.** Autointerp labels in this paper should be read as a coarse summary of a component's most salient behavior, not as a complete or precise description. The labeler sees only sampled activating examples and aggregate token statistics; it does not see the component's effect on downstream computation, and it has no access to the target model's weights. Labels are also bounded at $8$ words by construction. Individual labels can therefore miss real behaviors of the component (we point out one such case in <ref>sec:attn-analysis</ref> for <comp key>1.attn.q:149</comp> and <comp key>1.attn.q:497</comp>) or describe a component by a correlate of its true role. We use these labels as navigational scaffolding — to find candidate components for a given behavior and to give the reader a quick gloss — but every claim about a specific component made in the body of the paper is backed by direct inspection of activations, weights, or attribution graphs, not by the label alone.
