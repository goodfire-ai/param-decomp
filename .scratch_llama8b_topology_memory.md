# Llama-3.1-8B MLP decomposition — memory & topology vs the GPT-2 XL run

Scope: decompose the **3 SwiGLU matrices of one MLP** (`gate_proj`, `up_proj`, `down_proj`)
at **layer 18** of Llama-3.1-8B, CI fn sized to **10× the targeted params (≈1.76 B)**.
Relate to the live GPT-2 XL q/k run `p-b6505e9c` ("big512", 224 GPU). Companion estimator:
`.scratch_llama8b_mem_estimator.py` (`uv run python .scratch_llama8b_mem_estimator.py`).

**Status of the numbers.** Resident memory is *exact* (param counts × dtype/optimizer bytes).
Activation memory is a *dominant-term model* with one per-pool overhead multiplier fit to the
GPT-2 XL peaks (LW 37.6 / CI 131.9 / PPGD 103.1 GB). The LW (×1.79) and CI (×1.34) multipliers
are believable allocator-reserve margins; **PPGD's ×5.06 means my PPGD activation model is
missing most of its footprint — treat PPGD projections as soft.** None of this is a measurement
of a Llama run; it can't be until the model is vendored (see §5). The *structural* conclusions
(resident floors, which pool binds, topology regime) are robust to the activation fudge.

---

## 1. The headline numbers

| Quantity | GPT-2 XL q/k (live) | Llama-8B 3×MLP @ L18 |
|---|---|---|
| Target model params | 1.56 B | **8.03 B** |
| Decomposed sites | 96 (q/k × 48) | **3** (gate/up/down × 1) |
| Targeted matrix params | 245.8 M | **176.2 M** |
| CI fn params | 2.64 B (10.8× mats) | **1.72–1.75 B** (10× mats) |
| `total_input_dim` (CI concat) | 153 600 | **22 528** |
| `total_c` (CI output head) | 98 304 | **3·C = 3 072 … 12 288** |
| V/U params (all sites) | 314.6 M | 56.6 M (C=1024) … 226.5 M (C=4096) |

Two opposite forces vs GPT-2 XL: the **target model grows 5×**, but the **decomposition shrinks
~32× in site count**. They land on different pools, and that completely reshuffles which pool binds.

---

## 2. Per-pool memory (predicted, B200 = 191 GB)

`bl` = per-rank batch (lw/ci/ppgd). Llama rows carry GPT-2 XL's fitted overheads.

| Run | CI peak | LW peak | PPGD peak |
|---|---|---|---|
| **GPT-2 XL big512** (bl 64/16/8, fp32 tgt) | **131.9** ← binds | 37.6 | 103.1 |
| Llama, C=1024, **fp32** tgt, bl 8/8/4 | 78 | 59 | **174** ← tight |
| Llama, C=1024, **bf16** tgt, bl 16/16/8 | 62 | 37 | 119 |
| Llama, C=4096, **fp32** tgt, bl 8/8/4 | 81 | 65 | ~178 |
| Llama, C=4096, **bf16** tgt, bl 16/16/8 | ~65 | ~40 | ~123 |

### The single biggest structural change: the frozen target is now a per-pool floor
The frozen 8 B target sits resident on **every** pool:
- **fp32 → 29.9 GB**, **bf16 → 15.0 GB** per pool.
- For GPT-2 XL it was 5.8 GB — noise. For Llama it's the **largest single resident item on
  LW and PPGD**, and #2 on CI behind the CI fn.

→ **Lever #1: cast the frozen target to bf16.** It's frozen and only ever consumed under bf16
autocast, so fp32 master weights buy nothing. This halves the resident floor on all three pools
(saves ~15 GB/rank) and is the difference between PPGD being tight (174) vs comfortable (119).
`build_target` currently leaves it fp32 (`experiments/lm/run.py:148`, just `.eval()`); a
`.to(bfloat16)` on the frozen target is the cheapest win available.

### The CI pool stops being the bottleneck
This is the surprising, dominant result. For GPT-2 XL the CI pool **was** the binding constraint
(131.9 GB; the 2.64 B CI fn replicated per rank — see [[project_xl_b48_production_run]]). For
Llama the CI fn is *smaller* (1.72 B) **and its activations collapse with the site count**:

| CI activation term | GPT-2 XL (96 sites) | Llama (3 sites) |
|---|---|---|
| H-cache (fp32, ×2 prefetch) | 18.8 GB | 1.4 GB |
| concat (fp32) | 9.4 GB | 0.7 GB |
| CI values (low/up/pre) | 9.0 GB | 0.14 GB |
| g_CI recv (fp32) | 12.0 GB | 0.19 GB |

CI activation falls from ~53 GB to ~3–6 GB. **The CI pool goes from 131.9 → ~62–80 GB** and is
no longer the constraint. (Aside: at C=1024 the 1.76 B CI fn is **30× the V/U params** it
predicts and produces only `3·1024` outputs — very over-parameterised for its job. At C=4096
it's 8× V/U, comparable to GPT-2 XL. Harmless now that CI isn't binding, but worth a sanity
check on whether 10×-of-target-mats is the right CI sizing heuristic when there are few sites.)

### The new binding pool is PPGD (and it's the least-trustworthy estimate)
PPGD carries the frozen target + a full V/U replica + the (un-checkpointed) recon forward. With
the ×5.06 fudge it lands at 119 (bf16 tgt) to 174 (fp32 tgt). The fudge was fit on a regime
with 96 sites and the decomposed layer at 0 (full-model autograd graph); Llama has 3 sites and
layer 18 (≈half-model graph), so the carried fudge probably **over**-estimates Llama PPGD — i.e.
119/174 are likely conservative. Still, PPGD is where to spend the first real measurement.

## 3. Activation & autograd-graph effects of targeting layer 18

The recon losses (stochastic-recon on LW, PPGD) compute **KL on logits**, so LW/PPGD must run a
**full Llama-8B forward** even though only one MLP is decomposed. Consequences:

- **Compute pole moves to the full 8B forward.** GPT-2 XL LW swapped cheap q/k matmuls but still
  ran the whole 1.5 B forward for KL; Llama LW runs a full **8 B masked forward + backward**,
  ~5× the GPT-2 XL forward FLOP, but with only **3 component injections** (joint routing,
  `n_samples=1` → one forward). PPGD runs **3** such forwards (2 warmup + 1 final), un-checkpointed.
- **Layer 18 ⇒ shorter autograd graph.** Layers 0–17 run clean under `no_grad` (their output, the
  input to layer 18, is cached once); the backward graph spans only **layers 18–31 + final norm +
  lm_head (14/32 blocks)**. This roughly **halves** the recon activation vs decomposing layer 0.
  So Oli's "layer 18 shouldn't matter much" is right on compute but **favourable** on memory —
  decomposing an early layer would roughly double LW/PPGD recon activation. (Modelled in the
  estimator via `graph_layers = n_layers − decomposed_layer`.)
- **128 k vocab makes fused-KL chunking essential.** Full logits `[bl,1024,128256]` are 4 GB
  (bf16) at bl=16 — ×2 for pred+target. `use_fused_kl: true` (chunked) keeps it to ~1–2 GB; with
  Llama's 2.5× GPT-2 vocab this is load-bearing, not optional.

## 4. Topology regime change: only 3 sites

GPT-2 XL spread 96 q/k sites across 128 LW ranks (16 block-groups × 6 sites × DDP8). **Llama has
3 matrices.** LW's site axis is gone: at most 3 block-groups, or **one group owning all 3** ×
DDP. LW parallelism is now almost entirely **DDP (batch-split), hard-capped at `batch_size`**
(per [[project_b16_200k_topology_sweep]]). CI/PPGD were always batch-only.

**This is a small run, not a 224-GPU run.** Everything fits comfortably once the target is bf16,
and there's little to parallelise across. A reasonable first cut (batch_global = 64):

- **LW**: 1 block-group, all 3 sites, DDP4 → 4 ranks, bl_lw=16.
- **CI**: n_ci = 64/16 = 4 ranks, bl_ci=16.
- **PPGD**: n_ppgd = 64/8 = 8 ranks, bl_ppgd=8.
- ⇒ **~16 GPUs** (2 nodes), all pools < 130 GB with bf16 target.

Cross-pool divisibility holds (4 | 4, 4 | 8 etc.). This is well under the 8-GPU soft cap concern
only if scaled down; for a real run 16 GPUs is modest. The point: the GPT-2 XL machinery is
*over-built* for this problem — the expensive part (96-site CI fan-out + comm) largely evaporates.

## 5. Feasibility blocker: the vendored path is GPT-2-only

The ckpt/compile-compatible 3-pool path runs on **`LMComponentModel`**
(`experiments/lm/vendored/component_model.py`), which hardcodes `GPT2Simple` +
`componentize_gpt2` (`vendored/gpt2.py`): `ComponentCausalSelfAttention` / `ComponentMLP` /
`ComponentBlock` / `ComponentGPT2` thread `mask_infos` through a GPT-2 block loop. **There is no
`componentize_llama`.** `llama_simple.py` exists as a *vendored target* (SwiGLU, RMSNorm,
RoPE+GQA) but is **not** componentized.

To run this we need a Llama vendoring pass mirroring `vendored/gpt2.py`:
- `ComponentSwiGLUMLP` swapping `gate_proj` / `up_proj` / `down_proj` for `ComponentLinear`
  (note `down_proj`'s input is the 14 336-wide intermediate — the CI input for that site).
- `ComponentLlamaBlock` / `ComponentLlamaSimple` threading `mask_infos` + the collect path
  (`pre_weight_acts`, `forward_with_output_acts`) and `enable_activation_checkpointing`.
- Attn/RMSNorm just pass through (not decomposed here), so this is lighter than the GPT-2 port —
  only the MLP needs component leaves.
- A `from_hf_pretrained` on the vendored Llama (the `HFWeightsInVendored` target kind already
  expects it) to load real Llama-3.1-8B weights.
- `LMComponentModel` generalised off `GPT2Simple` (or a sibling `LlamaComponentModel`).

This is the actual gatekeeper — memory is the easy part.

---

## 6. Recommended sequence

1. **Vendor Llama for components** (`componentize_llama`, §5) — the only hard prerequisite.
2. **Cast the frozen target to bf16** (§2, lever #1) — halves the resident floor on every pool.
3. **1-rank memory probe** to replace the fudged activation model (esp. PPGD's ×5.06) with real
   `torch.cuda.max_memory_allocated` per pool — per the house rule, measure before sizing.
4. **Small topology** (§4): ~16 GPUs, bf16 target, bl 16/16/8, C∈{1024,4096}. CI is no longer
   binding, so spend the batch where recon quality wants it.
5. Open question to settle empirically: is "CI fn = 10× target-matrix params" the right heuristic
   at 3 sites? It yields a CI fn 30× the V/U params at C=1024 — possibly more capacity than a
   3-output predictor needs.
