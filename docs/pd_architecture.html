End-to-End Run Flow

There is one user-facing CLI — pd-run — and one training function — run_pd(). pd-run submits a SLURM job by default; each task invokes the internal worker module param_decomp.experiments._worker, which loads the driver and calls run_pd. pd-run --local skips SLURM and runs the worker in-process. A notebook can also import run_pd directly, bypassing drivers entirely.

What happens, in order

  1. pd-run resolves its input source into a Run: a built-in experiment name (looked up via discover_experiments()), --config_path PATH reading a YAML that declares its driver via a top-level driver_path: field, --rerun PATH reading the same shape from a saved run_config.yaml, or --sweep_generator_path FILE.py:func calling a generator that returns a SweepSpec of Runs.
  2. With --local, pd-run calls _worker.run_experiment(run) in this process. Otherwise it calls launch_slurm(...), which (for sweeps) snapshots the materialized SweepSpec to disk, creates a git snapshot branch, and submits a SLURM array — one task per run. Each array task invokes python -m param_decomp.experiments._worker --run_json '{...}'.
  3. _worker.run_experiment loads the driver, checks that run is an instance of the driver's config_type, builds the PDTarget and train/eval dataloaders, and calls run_pd().
  4. run_pd() creates PARAM_DECOMP_OUT_DIR/decompositions/<run_id>, writes run_config.yaml and all artifacts via save_pre_run_info(), starts W&B if configured, then trains.
  5. A direct run_pd() call from a notebook skips the driver entirely. The Run defaults to Run(driver_path=None, pd=..., logging=..., runtime=...); the run then reloads via load_component_model(path, target=...).

Saved Run and Reload

Reload picks up where the first diagram left off. Its starting box — Saved run directory — is the same green decompositions/<run_id>/ the training flow ended with. From there, three calls turn that directory back into a working ComponentModel: PDRun.from_path parses the run spec, load_target rebuilds the target via the driver, and load_model stitches the checkpoint onto it.

load_component_model(path) is shorthand for steps 1–3 chained together: PDRun.from_path(path).load_model().

Drivers no longer bundle target artifacts beside the checkpoint. build_target always fetches from upstream (wandb pretrain run, HuggingFace, disk), so saved PD runs depend on their upstream continuing to exist — the wandb run path / HF model name in the target config is the pin.

No driver in the saved Run? The run came from a direct run_pd() call. You must pass target=... to load_component_model(); pd_run.run is a bare Run (not a driver-specific subclass) and pd_run.driver is None.

The Three Concerns

Algorithm config

PDConfig owns losses, optimizer, schedules, CI architecture, module patterns, W&B. It never references a target model or dataset.

Experiment recipe

A driver-specific Run subclass (e.g. LMRun, TMSRun) adds target and data fields describing where the target comes from and what the data is. A driver turns the recipe into runtime objects: a PDTarget and dataloaders.

Runtime orchestration

One entry point (pd-run, on SLURM by default or in-process with --local) and one notebook escape hatch (direct run_pd) converge on a single training function and produce a saved run that PDRun.from_path / load_component_model can reload.

Entry Points

Entry Source When to use
pd-run <experiment> experiments/runner.py Run a built-in experiment by name on SLURM. Auto-resolves driver + YAML.
pd-run --config_path PATH experiments/runner.py Run a custom YAML. The YAML declares its driver via a top-level driver_path: field — there is no separate CLI flag.
pd-run --rerun PATH-OR-URL experiments/runner.py Rerun a saved run (local path or wandb URL). Driver + config are read from the run's run_config.yaml.
pd-run ... --local experiments/runner.py Run in-process; skip SLURM and the git snapshot. Required off cluster. Incompatible with --sweep_generator_path and with runtime.dp.
pd-run --sweep_generator_path FILE.py:func [--n_agents N] scripts/run_slurm.py SLURM array sweep over a Python-generated SweepSpec. The generator is a zero-arg callable returning a list of Run objects; see sweeps/cartesian.py for the built-in Cartesian helper.
python -m param_decomp.experiments._worker experiments/_worker.py Internal: the per-task entry point that each SLURM array task invokes.
run_pd(config, logging_config, runtime_config, target, ...) run_pd.py Notebook / scripting: skip drivers, supply your own PDTarget + dataloaders. Pair with load_component_model(path, target=...) for reload.
load_component_model(path) / PDRun.from_path(path) saved_run.py Reload a saved run.

The shell entry point is wired in pyproject.toml:

pd-run = "param_decomp.experiments.runner:cli"

Object Catalogue

Three Configs: PDConfig / LoggingConfig / RuntimeConfig

param_decomp/configs.py

The PD config space is split by what each field affects, so it is always clear which knobs change the algorithm vs the substrate vs only observation:

  • PDConfig — algorithm: losses (loss_metrics), custom metric imports (metric_modules), CI function (ci_config), module decomposition patterns (module_info), LR schedule, batch sizes, seed. Flipping any field here changes what algorithm runs.
  • RuntimeConfig — compute substrate: autocast_bf16, device, dp. Perturbs numerics without changing the algorithm. Config-only — no CLI overrides.
  • LoggingConfig — observation: cadence (*_freq), eval_batch_size, ci_alive_threshold, eval-only metrics (eval_metrics), wandb_run_name, view_meta. Never touches the optimizer.

The W&B project is not part of the Run — it is a deploy-time parameter (which account/team to log to), passed via --project to pd-run or wandb_project= to run_pd.

Metrics

param_decomp/metrics/

Built-in metrics live under param_decomp/metrics/builtin/ and self-register via @register_metric (see metrics/registry.py). A validator on PDConfig first discovers built-ins, then imports each dotted module listed in pd.metric_modules, then resolves loss_metrics (on PDConfig) and eval_metrics (on LoggingConfig) by registered class name. This lets experiment configs pass user-defined metrics without editing the core package. 

pd:
  metric_modules:
    - my_project.pd_metrics
  loss_metrics:
    MyCustomLoss:
      coeff: 0.1
      scale: 3.0
logging:
  eval_metrics:
    MyCustomEvalMetric: {}

Loss metrics use config classes that subclass LossMetricConfig and require coeff when used for training. Metrics already listed under loss_metrics are evaluated automatically and should not be repeated under eval_metrics.

Run (and driver-specific subclasses)

param_decomp/run.py

One Pydantic type — Run — represents "what a PD run is". The base class owns driver_path, pd, logging, and runtime; driver-specific subclasses add target and data. A mode="wrap" model validator on the base reads driver_path, loads the driver, and re-routes model_validate to driver.config_type, so callers always use Run.model_validate(data) / Run.from_file(path) and get back the right subtype.

  • LMRun(driver_path, pd, logging, runtime, target: LMTargetConfig, data: LMDataConfig)
  • TMSRun(driver_path, pd, logging, runtime, target, data)
  • ResidMLPRun(driver_path, pd, logging, runtime, target, data)

ExperimentDriver

experiments/driver.py

Stateless adapter: turns a Run into runtime objects.

class ExperimentDriver[RunT: Run](Protocol):
    name: ClassVar[str]
    config_type: ClassVar[type[Run]]

    def build_target(self, run: RunT) -> PDTarget: ...

    def build_dataloaders(
        self, run: RunT, *,
        train_batch_size: int, eval_batch_size: int,
        dist_state: DistributedState | None = None,
        device: str = "cpu",
    ) -> tuple[DataLoader[Any], DataLoader[Any]]: ...

Drivers always fetch from upstream (wandb pretrain run, HuggingFace, …); reload calls them exactly like a fresh run. Drivers are loaded by import path via load_driver("pkg.module:Driver").

PDTarget

models/batch_and_loss_fns.py

The bundle run_pd consumes:

  • model: nn.Module — the target model whose parameters we decompose.
  • run_batch — function (model, batch) → output. Helpers: run_batch_passthrough, run_batch_first_element, make_run_batch(output_extract).
  • reconstruction_loss — function comparing target vs reconstructed outputs. Helpers: recon_loss_mse, recon_loss_kl.
  • tied_weights: list[tuple[str, str]] | None — optional weight-tying pairs.

SweepSpec

param_decomp/sweeps/spec.py

Materialized output of a sweep generator: a description plus runs: list[Run]. All runs in one SweepSpec must share a driver_path and a runtime block (asserted in __post_init__). The launcher writes the spec to PARAM_DECOMP_OUT_DIR/sweeps/<launch_id>/spec.yaml before submitting the array.

PDRun

param_decomp/saved_run.py

Handle to a saved run. Loads the Run eagerly; driver/target lazily.

class PDRun:
    path: Path
    run: Run
    checkpoint_path: Path

    @classmethod
    def from_path(cls, path: ModelPath) -> "PDRun": ...

    driver:    ExperimentDriver | None    # via run.driver_path
    pd_config: PDConfig                   # property
    name:      str                        # driver.name or "custom"

    def load_target(self) -> PDTarget: ...
    def load_dataloaders(self, *, train_batch_size, eval_batch_size, ...) -> tuple[DataLoader, DataLoader]: ...
    def load_model(self, target: PDTarget | None = None) -> ComponentModel: ...

Experiment Discovery

experiments/discovery.py

Built-in experiments are discovered by walking param_decomp/experiments/<kind>/. A subdir qualifies as a "kind" iff it contains an experiment.py. Each [!_]*.yaml next to that file becomes a registered experiment.

  • Name = YAML stem with trailing _config stripped (tms_5-2.yaml → tms_5-2).
  • Driver path = param_decomp.experiments.<kind>.experiment:Driver — strict convention, not configurable. 
@dataclass(frozen=True)
class DiscoveredExperiment:
    name: str          # e.g. "tms_5-2"
    kind: str          # e.g. "tms"
    config_path: Path  # repo-relative path to the YAML

The YAML itself declares its driver_path as a top-level field; discovery only resolves name → YAML. Duplicate names across kinds raise an assertion.

SLURM Launcher Flow

When pd-run isn't given --local, it calls launch_slurm in param_decomp/scripts/run_slurm.py. The launcher produces one or more SLURM tasks; each task invokes python -m param_decomp.experiments._worker with a driver import path and a JSON config blob.

StageBehavior
Input resolution runner._resolve_source turns the CLI flags into a raw config dict that is then validated into a Run. Exactly one of positional <experiment>, --config_path, --rerun, or --sweep_generator_path must be set.
Sweep expansion For --sweep_generator_path, imports the absolute file path and calls the named zero-arg function. The function returns a SweepSpec(runs=[...]); all runs must share a driver_path and a runtime block. Not W&B sweep agents.
Spec snapshot The materialized SweepSpec is written to PARAM_DECOMP_OUT_DIR/sweeps/<launch_id>/spec.yaml for reproducibility.
Git snapshot One snapshot branch per launch for reproducibility (especially multi-node).
Command generation Dispatches on runtime.dp: plain python -m param_decomp.experiments._worker, single-node torchrun --standalone --nproc_per_node=N, or multi-node srun + torchrun.
Submission Single SLURM script for one Run; SLURM array (capped by --n_agents) for a SweepSpec, one task per run.

Command shapes

# Single-process
python -m param_decomp.experiments._worker --run_json '{...}'

# Single-node DDP (runtime.dp = 4)
torchrun --standalone --nproc_per_node=4 --master_port=... \
  -m param_decomp.experiments._worker --run_json '{...}'

The run JSON is the serialized Run: driver_path, pd, logging, runtime, plus driver-specific target / data. view_meta lives under logging.view_meta; the W&B project is passed separately via --project on the launcher.

Custom Drivers

You don't need to touch core code to add an experiment — just write a driver, declare it at the top of your YAML, and point pd-run at the YAML: 

# my_config.yaml
driver_path: my_pkg.my_exp:MyDriver
pd: {...}
logging: {...}
runtime: {...}
target: {...}
data: {...}
pd-run --config_path my_config.yaml

A driver is anything that satisfies the ExperimentDriver Protocol. See experiments/tms/experiment.py for a complete reference:

            tied_weights=_tied_weights(target_model),

        ...

The driver import path is part of the saved Run, so the run is reloadable via load_component_model(path) with no explicit target=.

If you don't need pd-run, sweeps, or post-processing tooling, call run_pd directly and skip drivers entirely — see the README's "Custom experiments" section. Those runs reload with load_component_model(path, target=...).

Saved Run Layout

Saved runs live under PARAM_DECOMP_OUT_DIR/decompositions/<run_id>/ (cluster: /mnt/polished-lake/artifacts/mechanisms/param-decomp/; local: ~/param_decomp_out/). 

decompositions/<run_id>/
├── run_config.yaml          # Run: driver_path + pd + logging + runtime + target + data
└── model_<step>.pth           # PD checkpoints (one per save_freq + final)

sweeps/<launch_id>/
└── spec.yaml                  # SweepSpec snapshot (sweep launches only)

Drivers no longer bundle target artifacts beside the checkpoint — build_target always fetches from upstream, so the wandb run path / HF model name in target is the only pin.

A typical run_config.yaml:

driver_path: param_decomp.experiments.lm.experiment:Driver
pd:
  seed: 0
  loss_metrics: {...}
  ci_config: {...}
  module_info: [...]
  ...
logging:
  wandb_run_name: seed=0
  view_meta: {}
  eval_metrics: {...}
  ...
runtime:
  autocast_bf16: true
  device: cuda
  dp: null
target: {...}
data: {...}

Reload usage

pd_run = PDRun.from_path("wandb:entity/project/runs/abc123")
pd_run.run                # Run (driver-specific subclass, e.g. LMRun)
pd_run.pd_config          # PDConfig (always available)
pd_run.driver             # ExperimentDriver | None  (None for notebook runs)
target = pd_run.load_target()        # driver.build_target(run)
loaders = pd_run.load_dataloaders(...)
model = pd_run.load_model()          # ComponentModel.from_checkpoint(...)

# Shortcuts
model = load_component_model("wandb:entity/project/runs/abc123")               # driver-backed
model = load_component_model("/path/to/run", target=my_target)                 # notebook-style run
