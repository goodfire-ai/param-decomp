Three-Pool Distributed Training

How the param_decomp_lab/three_pool/ subsystem splits a decomposition across three heterogeneous GPU pools — what lives where, and what crosses the wire when.

CI pool Layerwise (V/U) pool PPGD pool

1 · TL;DR & the big idea

Instead of every rank holding the whole model and data-parallel-sharding the batch (the old DDP), the world is partitioned into three rank-disjoint pools, each specialised to one part of the PD (VPD) loss. They run concurrently and exchange tensors point-to-point each step. The motivating constraint: a global, shared-transformer CI function that spans all decomposition sites is too big to replicate next to a full set of V/U components — so the CI fn gets its own dedicated, replicated pool, while V/U sites are sharded across a second pool, and the (memory-hungry, full-model) PPGD adversary gets a third.
Terminology — paper ↔ this doc. This doc describes the implementation; the VPD paper names the same pieces as below. Pool names (CI / LW / PPGD) are infrastructure, not paper concepts.
This doc / codeVPD paper

V/U components (ComponentModel, components, drop_components)rank-1 parameter subcomponents (the U·Vᵀ matrices). NB: "components" in the paper are post-hoc clusters of subcomponents — a different thing.

Each pool optimises a different set of parameters:

  • CI optimises the causal importance function (CI fn), driven by the importance-minimality loss plus gradients fed back from the two reconstruction pools.
  • LW optimises the V/U subcomponents (the decomposition weights), via the per-site layerwise stochastic-reconstruction loss + the parameter-faithfulness (Δ-L2) loss.
  • PPGD runs the Persistent-PGD adversary — the adversarial-reconstruction loss (full-model reconstruction under adversarially-optimised ablation masks), contributing gradients to both V/U and the CI fn.

The whole thing is a single SPMD program: one launch (torchrun), one dist.init_process_group, and then each rank looks up which pool it belongs to and runs that pool's step function. The entrypoint is ThreePoolTrainer in three_pool/optimize.py.

2 · How this differs from the old single-pool DDP

Old single-pool DDP (param_decomp.optimize.Trainer)New three-pool (ThreePoolTrainer)
Rank roleEvery rank is identical — same code path.Ranks are partitioned into 3 disjoint pools, each running a different step function.
Model on each GPUFull ComponentModel (CI fn + all V/U + target) on every rank.Each pool keeps only its parameters: CI pool drops V/U; LW & PPGD drop the CI fn; LW further keeps only its owned sites.
BatchLoader shards the global batch across ranks.Loader replicates the full global batch to every rank (dist_state=None); each pool slices its own DP shard internally.
CommunicationOne all-reduce of gradients per step (standard DDP).Six typed cross-pool point-to-point exchanges per step + in-pool reductions, on a web of purpose-built process groups.
What's parallelData parallelism only.Data parallelism within a pool + functional parallelism across pools (CI fwd, LW recon, PPGD recon all run at the same wall-clock moment).
WhyModel fits on one GPU.A global shared-transformer CI fn (billions of params) can't co-reside with full V/U + PPGD on 80 GB.

The single-pool trainer still exists and is the right choice when the model fits. The three-pool path is the heavy-iron sibling for large LM decompositions with a global CI fn.

3 · The three pools at a glance

CI pool

replicated CI fn · DP across batch
  • Owns: the CI function + its AdamW state
  • Replicated across all CI ranks; each handles one batch shard
  • Computes causal importance values + the importance-minimality loss
  • Drops the V/U components entirely

Layerwise pool

V/U sharded by site · DDP within a block
  • Owns: V/U for its block group's sites + AdamW state
  • Sites partitioned across block groups; within a group V/U is DDP-replicated and the batch is sharded
  • Layerwise stochastic-reconstruction loss + parameter-faithfulness (Δ-L2)
  • Drops the CI fn

PPGD pool

full V/U replica · DP across batch
  • Holds: a full (all-site) V/U replica + the persistent adversarial sources
  • V/U here is transient — overwritten every step by LW's updated weights (no V/U optimizer)
  • Full-model PPGD warmup + adversarial reconstruction
  • Drops the CI fn

One convention pins the layout: rank 0 must be the leader of Layerwise block 0 (three_pool_run.py validator) — so the logging reductions can ship the CI and PPGD pools' losses to a single, well-known rank.

4 · What physically lives on each GPU

Every rank constructs a ComponentModel, then drops the parts its pool doesn't need before moving to GPU (the RNG draws for the dropped params still happen, so init matches single-pool exactly). All three pools keep the frozen target model for the local forward pass.

Resident stateCILWPPGD
Frozen target model (for target_fwd)✅✅✅
CI function weights + AdamW state✅ (replicated)— dropped— dropped
V/U components— dropped✅ owned sites only (DDP-replicated in block)✅ all sites (transient replica)
Components AdamW state—✅ owned sites— (no V/U optimizer)
PPGD adversarial sources + their optimizer——✅ (per-rank, batch-local)
Reads the full global batch each step✅ (slices its DP shard)✅ (slices its shard)✅ (slices its shard)

The drop happens in the constructor:

match self.ctx:
    case LWContext() | PPGDContext():
        self.component_model.drop_ci_fn()        # LW / PPGD keep V/U, lose the CI fn
    case CIContext():
        self.component_model.drop_components()    # CI keeps the CI fn, loses V/U
self.component_model = self.component_model.to(self._device)

So the union of leaders' parameters across pools is the full model — which is exactly what the checkpoint consolidation later stitches back together (§12).

Here's a real (small, for resumption testing) config — gpt2_small_3pool_async_consol.yaml — decomposing the q/k projections of a 12-layer GPT-2 across 8 GPUs:

rank 0LW block 0 · leader = global rank 0
rank 1LW block 0
rank 2LW block 1 · leader
rank 3LW block 1
rank 4LW block 2 · leader
rank 5LW block 2
rank 6CI pool
rank 7PPGD pool
LW: 3 block groups × 2 ranks (N_per_block = 2, N_blocks = 3). Block 0 owns layers 0–3's q&k, block 1 owns 4–7, block 2 owns 8–11.   CI: N_ci = 1.   PPGD: N_ppgd = 1.   batch_global = 2.

The topology is declared in YAML under runtime.topology:

runtime:
  topology:
    use_fused_kl: true
    ci_ranks: [6]
    ppgd_ranks: [7]
    layerwise_block_groups:
      - ranks: [0, 1]
        owned_sites: [h.0.attn.q_proj, h.0.attn.k_proj, ... h.3.attn.k_proj]
      - ranks: [2, 3]
        owned_sites: [h.4.attn.q_proj, ... h.7.attn.k_proj]
      - ranks: [4, 5]
        owned_sites: [h.8.attn.q_proj, ... h.11.attn.k_proj]

Production runs scale this same shape up — e.g. the GPT-2-XL configs run on the order of 100+ GPUs with a multi-billion-parameter global shared-transformer CI fn, larger N_per_block, and bigger N_ci/N_ppgd so each pool data-parallelises across a wider batch.

6 · The comm fabric: process groups

build_world (layout.py) constructs every NCCL process group once at startup, on every rank, and stores them on the immutable World. There are seven kinds of group:

Process groupMembersCarries
ci_pool_groupall CI ranksAVG all-reduce of CI-fn grads; SUM-reduce of importance-minimality terms; loss logging
layerwise_pool_groupall LW rankscross-block grad-clip norm; step_ms MAX; loss/memory logging
ppgd_pool_groupall PPGD ranksSUM-reduce of V/U grads; eval-metric reductions
block_group_groups[i]ranks in LW block iin-block DDP AVG of V/U+faith grads; in-block broadcast of received PPGD V/U grads
cross_pool_bcast_groups[i]{LW block i leader} ∪ all PPGD ranksleader-rooted broadcast of updated V/U from LW → PPGD (edge ⑥)
cross_pool_p2p_groupall ranksevery cross-pool point-to-point send/recv (edges ①–⑤ + eval); the snapshot barriers
default groupall ranksonly coarse barriers (sync_across_processes around eval)
Why a dedicated all-rank p2p group separate from the default group? NCCL wedges if eval-time barriers share a communicator with un-progressed cross-pool point-to-point work. Keeping all the p2p traffic on cross_pool_p2p_group and barriers on the default group means a barrier can never deadlock against an in-flight isend that its peer hasn't matched yet.
Load-bearing timeout. dist.new_group does not inherit the timeout from init_process_group — with timeout=None it silently uses NCCL's 10-minute library default. Since the 3-pool runs all its real collectives on these subgroups (never the default group), build_world threads an explicit pg_timeout (default 10 min, overridable via PD_3POOL_PG_TIMEOUT_S) into every new_group call. The invariant: the timeout must exceed the worst-case on-loop gap between collectives — now just the fast eval pass plus a checkpoint partial-write barrier.

One more startup subtlety: cross-pool broadcast groups are pre-warmed. First use of a new NCCL group blocks on a synchronous communicator init across all its members — even with async_op=True. In the loop, the V/U broadcasts could interleave with logging p2p and deadlock on that init. So _prewarm_cross_pool_bcast_groups fires a 1-element dummy broadcast on each, at setup, while every rank is still in lockstep.

7 · The six cross-pool edges

Each cross-pool exchange is one typed class in portals.py — its pack layout, routing, wire dtype, and process group all defined once, with the sender and receiver as two methods on the same class (so they can't drift). A pool only constructs the portal halves at its own endpoints, so an LW step physically cannot invoke a CI-pool send.

All cross-pool tensors travel as bfloat16 (WIRE_DTYPE) — half the bytes vs fp32; grads accumulate into fp32 .grad and are upcast on receive.

③LW → CIGradCiFromLayerwiseper-owned-site CI grads (stoch), per-LW-rank slice; stitched on CI sidesend / irecv p2p

Notice the symmetry: CI broadcasts values out to both recon pools (①②) and receives grads back from both (③④); those grads are summed into the single CI-fn backward. The recon pools exchange weights and weight-grads between themselves (⑤⑥): LW owns the V/U optimizer, PPGD borrows the weights, runs the adversary, and hands gradients back.

8 · Per-step choreography

The defining feature is concurrency: at any wall-clock moment all three pools are doing useful work. CI's importance-minimality + next-batch prefetch overlaps the recon pools' heavy lifting; the sends fire on the NIC while the GPU keeps computing.

Synchronised timeline (one step T)

Pools: LW · layerwise V/U CI · causal-importance fn PPGD · adversary Arrows = sends between pools: ⟶ values & weights ⟶ gradients Indices & symbols: T = training step (one global batch) · HT cached pre-weight activations · CIT causal-importance values · yT frozen target output (the KL reference) · ∇ gradient

What each pool does, in order

CI step

  • CI fn forward on cached H_T → CI values (graph retained)
  • ① ② async-send CI values to LW + PPGD
  • importance-minimality loss (SUM-reduced across CI pool, autograd-aware)
  • dead-time prefetch target_fwd(T+1) → H_{T+1}
  • ③ ④ recv g_CI from LW & PPGD; stitch onto local slice
  • g_CI_total = g_CI_LW + g_CI_PPGD
  • fused backward through CI-fn graph (imp_min via upper_leaky, downstream grads seeded on lower_leaky)
  • AVG all-reduce CI-fn grads → clip → AdamW
  • wait the ①② sends before storage reuse

LW step

  • ① post async irecv for CI values (overlaps the fwd)
  • target_fwd(batch slice) → L_T
  • faithfulness loss + backward (V/U-only, doesn't need CI)
  • wait CI recv; re-leaf as fp32 requires_grad
  • layerwise stoch recon, streaming one owned site at a time (bounds peak memory) → grads onto V/U and onto the CI leaves
  • ③ send g_CI back to CI pool
  • ⑤ recv g_VU from PPGD; add into V/U .grad
  • in-block AVG all-reduce → clip → AdamW
  • ⑥ async-ship updated V/U to PPGD

PPGD step

  • ② post async irecv for full-model CI values
  • target_fwd(batch slice); compute weight deltas
  • wait CI recv; re-leaf fp32
  • warmup: N inner PGD iterations refining the adversarial sources in place
  • final recon forward + one autograd.grad → raw g_V, g_U, g_CI, g_sources
  • scale each by its own normalization
  • ④ send g_CI to CI (fired first — it's on CI's critical path)
  • SUM-reduce g_VU within PPGD pool; ⑤ send g_VU to LW
  • final (N+1)ᵗʰ source step
  • ⑥ blocking recv of updated V/U from LW → copy into model
The cross-step dependencies. Almost everything fits inside one step. Only three edges force a wait between steps: CI's next forward needs (a) this step's CI-fn AdamW and (b) the prefetched H_{T+1}; and PPGD's next warmup needs the V/U shipped at the end of this step (edge ⑥, resolved within the step via PPGD's blocking recv).

9 · The wrinkle: 3-way batch slicing

Each pool data-parallelises the same global batch on its own axis, with arities N_ci, N_per_block (LW), N_ppgd. In general a CI rank's batch slice and an LW rank's slice don't line up, so the CI→LW and CI→PPGD exchanges are many-to-many along the batch dimension.

The config validator tames this by requiring cross-divisibility per edge: for each cross-pool edge, one arity must divide the other (either direction).

N_ci | N_per_block   OR   N_per_block | N_ci      # CI ↔ LW
N_ci | N_ppgd        OR   N_ppgd | N_ci           # CI ↔ PPGD

That guarantees every overlap is a whole, aligned sub-slice, reducing the routing to a clean one-to-K fan-out (and K-to-one reduction). All the geometry lives in one symmetric helper, BatchEdge (layout.py), which answers every routing question for both regimes:

RegimeMeaningFan pattern
CI coarse (N_ci ≤ N_down)each CI slice contains fanout = N_down/N_ci whole downstream slicesone CI rank fans a sub-slice out to K downstream ranks; grads stitch back K→1
CI fine (N_ci > N_down)each downstream slice contains fanout = N_ci/N_down whole CI slicesone downstream rank gathers from K CI ranks (concat) and scatters grads back to those K

The receiver holds a PendingCiValues — one packet in the coarse regime, fanout packets (each from a different CI rank) in the fine regime — and stitches them into per-site [b_local, seq, C_s] tensors on .wait(). Because the six portal methods all consume world.ci_lw_edge / world.ci_ppgd_edge, none of them branches on which arity is larger.

In the 8-GPU example: N_ci = N_ppgd = 1, N_per_block = 2. So CI is coarse for both edges — the single CI rank fans each batch half to the two ranks of every LW block, and sends its whole batch to the single PPGD rank.

10 · Gradient flow & the scaling subtleties

Three loss families produce gradients that must land, correctly scaled, on two parameter sets. The tricky part is matching single-pool's effective gradient at any topology.

Into the CI function

The CI-fn backward is seeded from three places:

  • importance-minimality — computed inside the CI graph on upper_leaky, SUM-reduced across the CI pool with the autograd-aware dist.nn.functional.all_reduce (forward sums; backward SUM-reduces the gradient across the CI pool, so each rank's seed is scaled by n_ci — which the final AVG all-reduce then cancels).
  • g_CI from LW (stochastic recon) — edge ③
  • g_CI from PPGD (adversary) — edge ④

CI assembles g_CI_total = g_CI_LW + g_CI_PPGD on its batch slice and injects it directly on lower_leaky via torch.autograd.backward(grad_tensors=...), then runs the imp_min seed (a diagnostic split into two backward calls — gradient accumulation is identical to one fused call). A final AVG all-reduce over the CI pool divides every seed by n_ci — which the per-rank scalings below are calibrated to cancel.

Into V/U

LW's V/U .grad accumulates faithfulness + layerwise-stoch locally, then adds the PPGD grad received over edge ⑤. An in-block AVG all-reduce syncs the DDP replicas, then AdamW steps, then the updated weights broadcast to PPGD (edge ⑥). PPGD itself never steps V/U — it only differentiates to produce g_VU and to refine its sources.

Why the odd denominators. Each pool's per-rank gradient is scaled so that, after the cross-pool sum/reduce, the CI fn and V/U see exactly the single-pool gradient — independent of how many ranks are in each pool. Concretely:
  • Stoch (LW): per-site denominator is n_positions · n_sites_total · n_per_block / n_ci. The n_per_block / n_ci factor is exactly 1 on a square topology and only corrects non-square runs (it compensates for the CI pool's later AVG all-reduce over n_ci).
  • PPGD V/U: scaled by coeff_ppgd / (n_examples_local · n_ppgd) — the 1/n_ppgd is what the in-pool SUM-reduce reassembles into the full-batch grad.
  • PPGD CI: that times n_ci — unlike V/U, the CI grad passes through the CI pool's AVG all-reduce, so it needs the same n_ci compensation as the stoch denom.
  • PPGD sources: scaled by 1 / n_examples_local only — no coeff, no 1/n_ppgd, because per_batch_per_position sources are per-rank-independent adversary state (each rank steps its own; they are not reduced).
  • Faithfulness (LW): divides by numel_global (not the rank-local numel) so the per-element grad scale matches single-pool.
The single autograd.grad on PPGD deliberately differentiates the unscaled recon sum and applies each consumer's normalization afterward — folding any one scaling into the differentiated scalar would silently mis-scale the others.

11 · The typed-DAG code architecture

The subsystem is layered so the SPMD program reads like its dependency DAG, and invalid states / orderings are type errors rather than runtime asserts.

FileOwns
layout.pyWorld — declarative topology, every process group, all batch-split routing math (BatchEdge). Identical on every rank; no per-rank fields.
role.pyPoolRole = CIRole | LWRole | PPGDRole — this rank's view. Each variant carries only the fields valid for its pool (no | None bag). CIRole has no owned_sites; LWRole has no slice_idx — reading the wrong one doesn't typecheck.
portals.pyone typed class per cross-pool edge (pack layout + routing + dtype + PG in one place); the three in-pool collectives; per-pool bundles (CIPortals/LWPortals/PPGDPortals) exposing only that pool's edges.
context.pyPoolContext = CIContext | LWContext | PPGDContext — bundles world + role + that pool's portals. The trainer matches it to dispatch.
step_{ci,layerwise,ppgd}.pyper-pool step bodies. Each is a sequence of typed phases where every phase consumes the prior phase's frozen output bundle — so e.g. "send CI grads before the backward populated them" is a type error.
optimize.pyThreePoolTrainer — construction wiring + per-step match ctx: dispatch + snapshot/resume.

What this makes unrepresentable: wrong-pool comms (an LW step has no handle to a CI-pool recv); reading a field that doesn't exist for the pool; send/recv pack-layout drift (one class owns both halves); and out-of-order phases within a step (each phase fn takes the prior phase's bundle as an argument).

12 · Checkpointing & resume

The save path is split so the train loop never blocks on a multi-GB read — the original cause of an NCCL-watchdog death (run p-a5b667e9) where a synchronous rank-0 read held everyone at a barrier past the timeout.

On the loop: snapshot() writes partials

Every rank writes a self-contained partial to scratch_dir/step_<S>/rank_<r>.pth:

  • model_params — only leaders contribute: LW block leaders write their owned sites' V/U, the CI pool leader writes the CI fn. (Every non-leader holds a replica, so it contributes nothing — the union across leaders is the full model.)
  • optimizer_by_name — this rank's optimizer state, name-keyed
  • ppgd — the adversarial sources (PPGD ranks only)

Rank 0 also writes meta.pth (configs + layout fingerprint + c_per_site). There are exactly two cheap barriers — one pre-write (so rank 0's mkdir+meta land first), one post-write rejoin — and no NCCL model gather and no rank-0 assembly. Neither barrier can overrun the watchdog.

Off the loop: consolidate_step() assembles

An async, CPU-only job (running inside the slow-eval SLURM job, before the eval pass) reads all of a step's partials, assembles the full ComponentModel state_dict + ThreePoolTrainingState, writes model_<S>.pth + training_<S>.pth, prunes old training files (keeping all model_*.pth), and deletes the scratch dir. It is idempotent and engineered to never hang (a hung off-loop job would hold GPUs forever): rank 0 assembles while other ranks file-wait with a bounded timeout and fail-fast on a .consolidate_failed sentinel. Partials persist on failure, so a crashed consolidation is re-runnable via python -m param_decomp_lab.three_pool.consolidate_cli <run> [--step N].

Resume: from_snapshot()

Each rank reads the consolidated training_<step>.pth, then extracts its own slice of the canonical state by key. Topology is validated against the saved fingerprint — but only the rank-invariant core (world_size / ci_ranks / ppgd_ranks / block count), because the comparison runs on every rank. If a run dies after a save but before consolidation finishes, resume from the previous consolidated step (≤ one save-interval of lost progress; the unconsolidated partials can be recovered manually).

13 · Evaluation

Eval reuses the same value-shipping fabric but in a thinner form (eval_step.py). Each pool only does the work backed by state it actually holds:

  • CI target_fwd → CI fn fwd → ship full CIOutputs (all three dicts) to PPGD via edge E.
  • PPGD target_fwd → weight deltas → recv CI → assemble a MetricContext → run every eval metric.
  • LW barriers through (reads the eval batch but discards it, to keep the loader in lock-step).

Metric all-reductions are scoped to ppgd_pool_group via use_reduction_group, so CI and LW never block on them. Results broadcast to rank 0 for logging. Coarse sync_across_processes barriers on the default group bracket the pass so non-PPGD ranks don't trip the tighter p2p-group timeout while PPGD grinds through slow metrics.

14 · NCCL hazards & why the design looks the way it does

A lot of the structure exists to dodge specific distributed failure modes that bit production runs:

HazardMitigation
Sub-groups silently using NCCL's 10-min default timeoutbuild_world threads an explicit pg_timeout into every new_group
Barrier deadlocking against un-progressed cross-pool p2pall p2p on a dedicated cross_pool_p2p_group; barriers on the default group
First-use communicator init on a bcast group deadlocking with concurrent p2ppre-warm every cross_pool_bcast_group with a dummy broadcast at setup
Synchronous 100 GB rank-0 checkpoint read overrunning the watchdogpartials on the loop, async CPU-only consolidation off it
torch.cuda.synchronize() draining in-flight async NCCL on side streamsper-event syncs only (flush_nccl_event_timings); avoided in eval barrier
Accidental .item() CPU↔GPU syncs serializing the pipelinemetrics computed as GPU tensors; .item() only on log steps; PD_SYNC_DEBUG guard available
Off-loop consolidation hanging and holding GPUs foreverrank-0-assembles + file-wait with bounded timeout + fail-fast sentinel

And the performance shape: the headline overlaps are CI's importance-minimality + next-batch prefetch running during the recon pools' heavy backward, and the NIC sends firing while the GPU keeps computing. Most remaining Python-blocking points are NCCL ops convertible to async_op=True kickoff + later wait (see the "remaining lack-of-dependency" notes at the end of DESIGN.md).
