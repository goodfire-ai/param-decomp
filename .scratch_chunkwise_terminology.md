# Chunkwise terminology cleanup — proposal

Trigger: rename the 3-pool "Layerwise pool" → "Chunkwise" (more faithful: it shards *sites* into
chunks, it is not per-layer), and rationalise the sites / sitegroups / routers / strategies
vocabulary in `three_pool/`.

## The root problem: "layerwise" means two unrelated things

1. **The 3-pool pool** (`LWRole`/`LWContext`/`step_layerwise`/`LayerwiseBlockGroup`/
   `LayerwiseLossStrategy`, `three_pool/`). This pool owns V/U and shards the decomposed **sites**
   across DDP rank-groups. It is **not** per-layer — a group owns an arbitrary chunk of sites.
   → genuinely a misnomer. **This is what becomes "chunkwise".**

2. **A core-library recon style** (`StochasticReconLayerwiseLoss`, `CIMaskedReconLayerwiseLoss`,
   `LayerwiseCiFn`/`LayerwiseCiConfig`, `param_decomp/`). Here "layerwise" = *reconstruct each
   decomposed layer's output independently* (vs `global` end-to-end recon). This is a real,
   correct axis, orthogonal to pools, and part of the stable core API. **Keep as "layerwise".**

These are orthogonal: the chunkwise pool *computes* a layerwise recon loss. Renaming both to
"chunkwise" would re-merge two concepts that should stay distinct. So the rename is scoped to
**`three_pool/` (the pool), not `param_decomp/metrics/` (the loss style).**

## Proposed vocabulary (layered)

### A. Sharding — who computes what (the "chunkwise" layer, `three_pool/`)
| concept | now | proposed | definition |
|---|---|---|---|
| one decomposed module | `site` ✓ | `site` (keep) | e.g. `layers.18.mlp.gate_proj` |
| a set of sites + the DDP ranks owning them | `LayerwiseBlockGroup` / `...Spec` | **`Chunk`** | the unit the pool shards over |
| the pool | "Layerwise pool" / `LWRole`/`LWContext` | **Chunkwise pool** / `ChunkRole`/`ChunkContext` | |
| the per-rank step fn | `step_layerwise` | **`step_chunkwise`** | |
| DDP replicas per chunk | `n_per_block` | **`chunk_dp`** | (CI/PPGD already think in pool size; this is the chunk's) |
| config: how sites split into chunks | `layerwise_block_groups: [{ranks, owned_sites}]` | **`sites_per_chunk: int`** | + derive (see config redesign) |
| a chunk's sites | `owned_sites` | **`chunk.sites`** | |

So "chunkwise" reads truthfully: *the pool shards the sites into chunks; each chunk is a
site-group replicated across `chunk_dp` ranks.*

### B. Recon orchestration — how one chunk reconstructs (the tangle Oli flagged)
| concept | now | proposed | why |
|---|---|---|---|
| per-position routing-mask generator (`masks.py`) | `Router` ✓ | `Router` (keep) | accurate |
| turn a chunk's sites → list of recon forwards | `RoutingPlan` (`PerSitePlan`\|`SubsetRoutingPlan`) | **`ReconPlan`** (`PerSitePlan`\|`SubsetReconPlan`) | it plans *recon forwards*, not just routing |
| fused-vs-unfused KL + lm-head bypass pair | `LayerwiseLossStrategy` | **`ReconLossStrategy`** | nothing layerwise about it — it's the KL-loss mode |

`ReconLossStrategy` is the worst current name: "Layerwise" there is pure noise (it's the
fused/unfused KL choice, used by *both* the chunkwise pool and the PPGD inner loop).

## Why this is "invalid states unrepresentable + meaningful info surfaced"
- One word per concept: **chunk** (sharding unit), **site** (module), **router** (mask gen),
  **ReconPlan** (forward list), **ReconLossStrategy** (KL mode). No "layerwise" doing 3 jobs.
- The config stops listing ranks/owned_sites (see `.scratch_3pool_config_redesign.md`):
  `chunkwise: { per_rank_batch, sites_per_chunk }` — chunks + ranks + site assignment all
  derived. Fold both refactors into one pass (same files: `config.py`, `optimize.py`,
  `layout.py`, `three_pool_run.py`).

## Scope of the rename (≈ files)
`three_pool/`: `config.py`, `layout.py`, `role.py`, `context.py`, `optimize.py`,
`step_layerwise.py`→`step_chunkwise.py`, `loss_strategy.py`, `routing_plan.py`→`recon_plan.py`,
`portals.py`, `reductions.py`, `eval_step.py`, `pd_config.py`, `consolidate.py`, `checkpoint.py`,
`CLAUDE.md`, `DESIGN.md`. Plus `experiments/lm/three_pool_run.py`, `experiments/lm/layerwise.py`
(the `pd-lm-layerwise` splitter — rename? it splits an LM into per-matrix configs; "layerwise"
there is the per-matrix sense → maybe `pd-lm-per-site`), config dir `_chunkwise/` (already!),
and the 3-pool tests. **Not** `param_decomp/metrics/*layerwise*` or `ci_fns.LayerwiseCiFn`
(deliberately kept — axis B above).

## Open forks for Oli (before the sweep)
1. **Unit name: `Chunk` vs `SiteGroup`?** Oli used both. `Chunk` pairs with "chunkwise" and is
   terse; `SiteGroup` is more literal (a group of sites). Lean `Chunk` (+ `chunk.sites`).
2. **Core-lib losses `StochasticReconLayerwiseLoss` etc. — keep "layerwise"?** Recommend KEEP
   (genuine per-layer meaning, stable core API). Only rename if you want one word globally.
3. **`RoutingPlan`→`ReconPlan`, `LayerwiseLossStrategy`→`ReconLossStrategy`** — agree, or
   different names?
4. **`pd-lm-layerwise` splitter** (`experiments/lm/layerwise.py`): it's the per-matrix-config
   SLURM-array splitter — "layerwise" = per-site there. Rename to `pd-lm-per-site` / leave?
