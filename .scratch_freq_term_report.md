# Importance-minimality "frequency term" (`L_freq`): git + code archaeology

Read-only investigation. No tracked code modified.

The freq term is the `beta`-weighted entropy-like term added to the `L_p`
sparsity penalty:

```
layer_loss = (per_component_mean + beta * per_component_mean * log2(1 + <SUM>)).sum()
per_component_mean = layer_sums / n_examples
<SUM>             = layer_sums = Σ_positions (ci + eps)**pnorm   (per component)
```

The whole question is **what `<SUM>` is — a per-rank LOCAL sum or the GLOBAL
full-batch sum** — because `log2` is concave, so the only value that matches the
VPD paper's `L_freq` derivation is `log2(1 + global_full_batch_sum)`.

## 0. Headline result (read this first)

The Background brief contained one assumption that is **false for this
codebase**, and it changes the whole conclusion:

> "in the 3-pool ... `get_distributed_state().world_size` may be the FULL world
> (e.g. 144) ... the pre-fix freq term was over-inflated by `full_world / n_ci`"

**The 3-pool NEVER used `get_distributed_state().world_size` for the freq term,
and was never over-inflated.** Since the very first 3-pool MVP
(`a8ee7b5d`/`f0a5beee`), `step_ci.py` has reduced `per_component_sums` over the
**CI process group only** (`ci_pool_group`, `n_ci_pool`) with an autograd-aware
`dist_fn.all_reduce`, and then passed `world_size=1` to `_finalize`. So the
3-pool always computed `log2(1 + true_global_CI_batch_sum)` — the correct
quantity. (Proof in §2 and §4.)

Consequently:

* **The fix commit `30f35b7f` is a pure rename for the 3-pool path** — it
  swaps the imported helper names (`_finalize`→`finalize_imp_min`,
  `_per_component_sums`→`per_component_lp_sums`, `_get_linear_annealed_p`→
  `annealed_pnorm`) and drops the now-redundant `world_size=1` kwarg. The math
  is byte-for-byte identical.
* **Both runs at stake ran the CORRECT freq term.** `p-05b1390b` (pre-fix code)
  and `p-063bd860` (post-fix code) are both **3-pool** runs whose CI-pool reduce
  produced the global sum. The `world_size` parameter that existed in
  `p-05b1390b`'s `_finalize` was passed the constant `1` by the 3-pool caller,
  so it had **zero effect** on that run.
* The `world_size` knob mattered **only on the single-pool path** — and there,
  the all_reduce fix (`0ea7beef`) had *already* superseded it before `30f35b7f`.
  `30f35b7f` only removed the dead/biased path that survived in the standalone
  app helper.
* **`main` is still on the biased path for single-pool DDP training** (neither
  `0ea7beef` nor `30f35b7f` is on main). See §1 and §3.

So the imp-loss difference between the two runs is **almost entirely the batch
change (16→48)**, not the normalization fix. (Quantified in §5.)

## 3. Which is correct, which is broken, and why

### The math
For a component, let the per-position contributions be `x_1,…,x_N` with
`x_i = (ci_i+eps)^p ≥ 0`, split across `R` ranks each holding `N/R` of them.
Global sum `S = Σ_i x_i`. The intended freq term (VPD `L_freq`, full-batch) is
`log2(1 + S)`.

* **Exact global (all_reduce SUM of per-rank sums):** each rank holds the same
  `S`, evaluates `log2(1+S)` once. Exactly the intended quantity. This is what
  the branch (pre- and post-fix) and the 3-pool do.
* **`local × W` estimator (`1da22a1a`):** rank `r` holds `s_r = Σ_{i∈r} x_i`
  and evaluates `log2(1 + s_r·W)`. With `W = R` and the loss then **averaged**
  across ranks by DDP, the logged/backpropped value is
  `(1/R) Σ_r log2(1 + R·s_r)`. By Jensen (concavity of `log2`) and the fact that
  `R·s_r` is an unbiased estimate of `S` only in expectation:
  `(1/R) Σ_r log2(1 + R·s_r) ≥ log2(1 + Σ_r s_r) = log2(1 + S)` iff the per-rank
  `R·s_r` straddle `S`. Concretely, `log2` concave ⇒ averaging the log of
  rank-scaled sums **over-estimates** `log2` of the true sum whenever per-rank
  distributions are non-uniform. So the estimator is **upward-biased**; the bias
  grows with per-rank heterogeneity and vanishes only when every rank's `s_r`
  equals `S/R` exactly. This is exactly what `0ea7beef`'s message describes
  ("Jensen-upward-biased ... diverged from the eval-time compute() value ...
  measurably so at our scale").

### Verdict
* **Wrong number AND wrong gradient (training):** `main`'s single-pool training
  path. The standalone `importance_minimality_loss()` backprops the biased
  `log2(1 + local·W)` term — so it logs an inflated imp loss **and** applies an
  inflated sparsity-pressure gradient. Direction: too much sparsity pressure
  (penalty over-stated), growing with rank count / heterogeneity.
* **Correct (everything on the branch):** Metric `update`/`compute` (single-pool)
  and the 3-pool `step_ci.py` all compute the exact global sum. The fix
  `30f35b7f` did not change the number or the gradient for any real branch
  caller — it deleted a dead biased code path and renamed helpers.
* **The two runs:** both correct. `p-05b1390b` ran pre-fix-but-post-`0ea7beef`
  3-pool code; `p-063bd860` ran post-fix 3-pool code. Both reduced over the CI
  pool. The freq term in both is `log2(1 + true global CI-batch sum)`.

### Gradient vs logged value
The imp loss IS backprop'd (it's `coeff_imp * loss_imp` in `step_ci.py`'s fused
backward, and the autograd-aware `dist_fn.all_reduce` makes the global sum
differentiable w.r.t. each rank's local CI). So on the *biased* path the change
is **not** cosmetic — it alters the sparsity-pressure gradient on `ci`. But for
the branch and for **both runs at stake**, there was no biased path in play, so
there is no train/log distinction to make: the number logged equals the
quantity optimized, and it's the correct one.

## 5. Magnitude of the difference between the two runs

Both runs compute the correct `log2(1 + S_global)`. The freq term differs
between them for exactly **one** reason that's substantive (batch size) and
**zero** reasons from the normalization "fix" (no-op for 3-pool).

### (a) Normalization / world_size / Jensen change: ZERO
Because both runs used the CI-pool global reduce and `world_size=1`-equivalent
finalize, the `30f35b7f` change contributes **no** difference between them. The
Jensen-bias direction (the brief asks for it) is: on the *biased* estimator the
freq term is biased **upward** by `(1/R)Σ log2(1+R·s_r) − log2(1+S) ≥ 0` — but
neither run was on that estimator, so this term is 0 here. (Had `p-05b1390b`
been a single-pool *main* run it would have been inflated; it was not.)

### (b) Batch change 16→48: pushes imp UP (logarithmically)
`<SUM> = n_examples · mean = (batch_global · seq) · mean`. With seq=1024:
* `p-05b1390b`: n_examples = 16·1024 = 16,384
* `p-063bd860`: n_examples = 48·1024 = 49,152 (×3.0)

The `L_p` term is a **mean** (`per_component_mean`), so it's ~batch-invariant in
expectation. But the freq term is `mean · log2(1 + <SUM>)`, and `<SUM>` scales
linearly with batch for fixed `mean`. For a component with roughly stationary
`mean` across positions, tripling the batch adds **`log2(3) ≈ 1.585`** to the
`log2(1+<SUM>)` factor (for `<SUM>≫1`). So the per-component freq contribution
goes up by `+1.585·beta·mean ≈ +0.79·mean` (beta=0.5), i.e. the freq term is
**larger at batch 48 purely from the larger batch**, with no change in the
underlying CI distribution.

This makes imp loss **non-comparable across batch sizes** — a smaller imp number
at batch 48 reflects genuinely sparser CI, not the batch. The logged values are
consistent with this being dominated by CI dynamics rather than the +log2(3)
offset (e.g. `p-063bd860` step ~15k ≈ 1.6k vs `p-05b1390b` step ~25k ≈ 4.5k —
the post-fix run is *lower* despite the batch pushing it up, because the
optimization drove CI sparser; the raw early-step spikes 3.2e5 vs 3.5e5 are
dominated by the un-annealed initial CI, not the freq term).

### Net
* normalization-fix contribution to (p-063bd860 − p-05b1390b): **0** (no-op for
  3-pool).
* batch contribution (16→48): **+log2(3)·beta·mean per component** inside the
  freq term, i.e. pushes imp **UP**.
* The brief's framing "batch change pushes imp UP while the normalization fix
  pushes it DOWN" is only half-applicable: the batch direction is right; the
  normalization fix is a no-op for these runs (it would push DOWN only for a
  single-pool *main* run that had been using the biased `local×W` estimator).

## 6. Open uncertainties (stated honestly)

1. **Per-component `mean` stationarity.** The `+log2(3)` batch offset assumes
   `mean` (and the CI distribution) is roughly batch-invariant. CI is data- and
   training-step-dependent, so the exact freq-term delta between the two runs
   can't be isolated from training dynamics without recomputing the term on
   matched checkpoints/data. The +log2(3) is the *ceteris-paribus* offset, not a
   measured run-to-run delta.
2. **Whether `p-05b1390b` ever ran on truly pre-`0ea7beef` code.** Its snapshot
   (`06422ef6`, 2026-05-27 21:18) is *after* `0ea7beef` (2026-05-27 16:34) and
   contains the CI-pool reduce, so I'm confident it used the global sum. If the
   run was *launched* before its snapshot commit and resumed, an earlier
   sub-version could in principle have differed — but every 3-pool commit back to
   the MVP used the CI-pool reduce, so the conclusion is robust regardless.
3. **I did not exhaustively diff the standalone `importance_minimality_loss()`
   caller graph on the branch** beyond confirming the Metric and 3-pool paths.
   The fix-commit message states its sole caller is the (non-distributed) app;
   I take that at face value for the single-pool eval/app side. It does not
   affect either run.
4. **Logged `train/loss/imp` semantics.** I read raw values from
   `metrics.jsonl` to sanity-check direction; I did not re-derive the exact
   per-component breakdown or confirm whether the logged scalar includes the
   `coeff_imp` scaling vs raw `loss_imp` (in `step_ci.py` the logged
   `loss/imp` is `loss_imp.item()`, i.e. pre-`coeff_imp`). This doesn't change
   the qualitative magnitude story.
