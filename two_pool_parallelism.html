How parallelism works in two_pool/run.py

The 2-pool strategy splits the SPD training step across two disjoint groups of GPUs. Pool A owns the optimizer and computes the cheap, layerwise losses. Pool B holds a full replica of the model and runs the expensive Persistent-PGD reconstruction loss. They run their forward/backward passes in parallel on different batch slices and exchange CI activations, gradients, and updated weights each step.

Pool A — optimizer, layerwise loss Pool B — full replica, PPGD recon CI activations V/U + CI gradients Updated V/U weights async / overlapped

1 · Topology — who lives where

Pool A is organised into blocks. Each block owns a disjoint subset of the decomposed sites and replicates V/U for those sites across the block's ranks (in-block DDP). The global batch is split: each block processes one batch slice on its owned sites, and each pool-B rank processes another batch slice on the full model. Why blocks? Each A-rank only instantiates components for its block's owned sites (build_pool_a_module_path_info) — so memory scales with the block's site share, not the whole model. Pool B builds the full module path info (build_pool_b_module_path_info) because PPGD needs to forward through every decomposed layer.

2 · The cross-pool exchange (one step)

Within a single training step, A and B run their own forward/backward in parallel, pausing only for three exchanges: A sends CI to B, B sends V/U + CI gradients back to the site's owning A-rank, and A sends the freshly stepped V/U back to B. Two of those — the CI send and the weight send — are async: they post the transfer and let local compute run on top of it, only waiting when the buffer or the parameter is about to be mutated.

Three async overlaps. (1) Pool A's CI send is non-blocking; A only waits at the end of the step, after its own backward and optimizer step have run on top of the transfer. (2) Pool A's weight send fires after AdamW, and A doesn't wait until the start of the next step — overlapping the entire next forward on top. (3) Pool B posts irecvs for CI before the target forward, so the CI transfer overlaps the full-model forward — CI isn't needed until the re-leaf step.

a/0   Wait on previous step's async weight send

Before AdamW can mutate V/U this step, last step's async weight-send to pool B must have flushed. The wait is cheap because all the in-between work (forward, losses, backward, all-reduce) already overlapped the transfer.

_pending_weight_sends[0].wait()

a/1   Target + CI forward

Run the (frozen) target model and compute CI activations. Cache inputs for the CI function so its graph is retained for backward.

forward (target + CI fn)

a/2   Async-send CI to pool B

For every owned site, post non-blocking sends of the per-site CI tensor to each B-rank, sliced along batch so each B-rank gets only its own slice. Returns a list of work handles + holding buffers; A doesn't wait yet.

async_send_owned_ci_to_pool_b

a/3 — a/5   Three "home" losses

Faithfulness + importance minimality + layerwise stochastic recon. The stochastic recon is a serial loop over owned sites — that serial cost is exactly what we wanted to move off pool B. These phases overlap the in-flight CI send from a/2.

a/3 loss_faith a/4 loss_imp a/5 loss_stoch (per-site loop)

a/6   Receive grads from pool B

Per owned site: V/U gradient (full grad), and the ci_lower gradient for each B-rank's batch slice.

recv_grads_from_pool_b

a/7   Seed grads and run the combined backward

Manually assign comp.V.grad = v_grads[s], comp.U.grad = u_grads[s], then call autograd.backward on total_home while also injecting B's ci-grads into the CI tensors. The CI-fn graph receives the combined (stoch + ppgd) signal — identical to what the single-pool path would have produced.

torch.autograd.backward(tensors=[total_home, *ci_lower], grad_tensors=[None, *ci_grads])

a/8   In-block DDP all-reduce

V/U and the CI-fn parameters are replicated across the block's A-ranks. Average the gradients within the block group.

all_reduce_grads_in_block

a/9   AdamW step (fused)

One optimizer step covering both component params (V,U) and CI-fn params, on the synced gradients. fused=True uses a CUDA-fused AdamW kernel that is noticeably faster on H200 than the default foreach implementation.

optimizer.step()

a/10   Async-send updated V/U back to pool B

Post non-blocking sends for the new V/U of each owned site — to every B-rank — so the full replica there stays in sync. Do not wait. The wait happens at a/0 of the next step, after the next forward has already been overlapped on top of the transfer.

async_send_updated_weights_to_pool_b

a/11   Wait on this step's async CI send

The CI tensors backing the send from a/2 will be replaced next step; flush before the buffer references go out of scope.

ci_send_works[i].wait()

4 · Pool B step step_pool_b

Phase tags match the labels emitted by PhaseProfiler (e.g. b/1_post_async_recv_ci).

b/1   Post irecvs for CI (async)

Post the receives for per-site CI from each owning A-rank, then move on immediately. The transfer will overlap the target forward below — pool B doesn't need CI until the re-leaf step.

async_recv_ci_from_owners

b/2   Target forward (no grad, full model)

Run the full target model on the local batch slice with no_grad — we only need the activations as a PPGD target. Runs in parallel with the CI recvs above.

forward (full model, no_grad)

b/3   Wait on CI recvs, then re-leaf

By this point the CI recvs are typically already done. Wait on the work handles, then detach + clone the received CI tensors with requires_grad_(True) so we can ship CI gradients back.

b/4   PPGD warmup

Refine the persistent adversarial sources in PersistentPGDState in-place — these sources persist across training steps, which is the whole point of PPGD.

b/5   Compute PPGD recon loss

Run the recon loss with the refined sources. Scale by 1 / n_pool_b so a SUM-reduce across pool B equals the full-batch gradient.

b/6   Extract gradients via autograd.grad

One autograd.grad call against (V, U for all sites) + (CI scratch leaves for all sites) — no .grad pollution on shared parameters.

b/7   Persistent source step

Take a separate gradient w.r.t. the PPGD sources, then ppgd_state.step updates the sources for next round.

b/8   SUM all-reduce V/U within pool B

Pool-B ranks each saw a different batch slice; SUM-reduce gives the full-batch V/U gradient (already scaled by 1/N in b/5).

dist.all_reduce(SUM, pool_b_group)

b/9   Send grads to owning A-ranks

Per site: V/U grad to the site's owner block; per slice: CI grad to the rank that owns it for that slice.

send_pool_b_grads_to_owners

b/10   Receive updated V/U

Block until owning A-ranks ship the post-AdamW weights, then copy into the full local replica. Ready for next step.

recv_updated_weights_from_owners

6 · Why this is equivalent to a single-pool step

Invariant 1 — total CI gradient. Pool A's CI tensor has graph retained. The combined backward injects pool B's ci-grad alongside pool A's own home-loss CI-grad. The CI-fn sees ∂(L_home + L_ppgd)/∂CI — exactly what a serial single-pool run would compute.

Invariant 2 — total V/U gradient. Pool A seeds V.grad / U.grad with pool B's PPGD contribution, then the backward of total_home adds the home-loss contribution. Result: V.grad = ∂L_home/∂V + ∂L_ppgd/∂V, again matching the single-pool sum.

Invariant 3 — batch coverage. Pool A processes its block's slice of the global batch; pool B's ranks process the remaining slices and SUM-reduce within pool B. The 1/n_pool_b scaling on total_ppgd makes the SUM equal to a full-batch gradient.

7 · Profiling and perf knobs

PhaseProfiler

An optional PhaseProfiler wraps each phase in cuda.synchronize() + perf_counter. The labels above (a/0_wait_prev_weight_send … b/10_recv_weights) come from its phase(name) context manager. Synchronising serialises async ops, so turn it off for real wall-clock measurements — it's a diagnostic for finding the bottleneck phase, not a free measurement.

Other knobs

  • enable_tf32=True — sets torch.set_float32_matmul_precision("high"). ~2–3× matmul speedup on H200 with sub-ULP precision loss; safe for fp32 SPD training.
  • fused_optimizer=True — uses the CUDA-fused AdamW kernel (noticeably faster than the foreach default).
  • Block groups are now first-class BlockGroup objects in TwoPoolConfig.block_groups (instead of raw rank lists + a parallel owned-sites tuple) — the topology is now one tuple of well-typed entries.

8 · The shape of the orchestrator

optimize_two_pool initialises the layout, picks which side this rank is on, builds the right ComponentModel (sliced vs full), creates either an AdamW (pool A) or a PersistentPGDState (pool B), then loops: 

for step in range(n_steps):
    batch = batch_iter(step)
    if layout.my_pool == "a":
        step_pool_a(
            layout, component_model, optimizer, all_params, batch,
            pool_config, profiler=profiler,
        )
    else:
        step_pool_b(
            layout, component_model, ppgd_state, batch,
            pool_config, profiler=profiler,
        )

All the cross-pool plumbing — who sends what to whom, what slices, what groups — is hidden behind BlockDDPLayout. run.py stays at the same composition level as run_pd.optimize: it just wires the existing primitives under a different topology.
